weewx-celestial change history
------------------------------

8.3.6 (in progress)
------------------
- A station whose console clock runs fast is no longer accused of
  writing no backdrops.  Its archive records are stamped ahead of its
  own loop packets, so every backdrop it serves depicts a time the page
  has not reached; the page refuses them -- it will not draw a sky from
  the future -- and the star field freezes.  That much is right, but the
  line under the panel read "no newer backdrop has arrived", which sent
  the reader looking for a report cycle that was running perfectly the
  whole time.  The line now names this case as its own, and the manual
  has a section for it.
- On an archive interval the fragment spacing does not divide -- 350
  seconds, say, against 60-second slots -- the station rendered a sixth
  backdrop every report cycle that no page could ever ask for, and the
  last 50 seconds of each cycle showed the slot before.  The set now
  counts what it writes.  Every standard WeeWX archive interval divides
  exactly and is unaffected.
- The Next Visible Pass chart stops rewriting its dot's hidden state
  twice a second through the minutes after a pass ends (8.3.5 fixed the
  same churn in the hours before one rises).
- Drop-in over 8.3.5; no configuration change.

8.3.5 (2026/08/17)
------------------
- The page's clock is the loop packet's own timestamp -- and, before the
  first packet, the instant the page was generated for.  8.3.4 carried
  the station's clock forward between packets on the browser's
  stopwatch; nothing does now, so the time shown always belongs to the
  data beside it.  A browser test proves a viewer clock half an hour
  wrong, either way, changes nothing on the page.
- The countdown chips and the satellite rosters repaint as loop packets
  arrive (every refresh_rate seconds) rather than once a second; the
  tick remains for the motion between packets.  A page with no working
  loop feed stands still, and the LIVE badge says why.
- The header's separate running clock is gone; the "updated" stamp
  beside it is baked at generation in 24-hour HH:MM:SS.
- The sky dome can no longer show a sky the station has not reached.
  The page worked out which backdrop to ask for from the backdrop it
  was holding, and for the first moments of every report cycle that one
  belongs to the cycle before -- so it named that cycle's late slot, and
  since a backdrop's filename carries a slot number and no cycle, the
  station answered out of the cycle it now held: a sky up to a cycle
  into the future, kept until the real time caught up to it.  The slot
  now follows from the station's clock and the archive interval alone
  (report cycles are generated for an archive record, so every cycle
  begins on an interval boundary), and a backdrop depicting a time the
  station has not reached is refused.  A laptop waking from sleep or a
  tab returning from the background steps to the right backdrop as soon
  as the loop feed catches up.
- The backdrop is fetched only when the sky is due to step -- when the
  slot the station's clock calls for is not the one already showing --
  instead of once a minute regardless.  A page in step with its station
  fetches nothing; a page whose station has stopped writing fetches
  nothing either, since its clock has stopped with it.  On an archive
  interval longer than ten minutes, where the slots are spaced further
  apart than the old once-a-minute refetch, most of those fetches
  returned a sky the page already had and were discarded.
- The Next Visible Pass chart no longer rewrites its dot's position and
  look once a second through the hours before a pass rises.  The chart
  stands as the station drew it, and is now restored once rather than
  continuously.
- Drop-in over 8.3.4; no configuration change.

8.3.4 (2026/08/16)
------------------
- The live page now reads one clock, and it is the station's.  Every
  instant the page reasons about -- a satellite pass's rise and set, a
  countdown chip's target, the roster's "overhead now", the header
  clock -- is written by the station, so the page no longer measures any
  of them against the viewer's own clock, which it has no reason to
  trust.  It asks the browser only how long something took, never what
  time it is.  A viewer whose clock was wrong could previously read
  every countdown off by the same amount, see the marks on the dial and
  the dome extrapolated up to two minutes from where they belong, and
  find a perfectly live feed labeled "120s ago"; all three now show
  the same page a correct clock shows.  Nothing is configured and
  nothing looks different on a machine whose clock is right.
- The clock is anchored on each loop packet's own timestamp and carried
  forward between packets; before the first packet arrives it is
  anchored on the page's own generation instant, so the countdown chips
  tick from the moment the page loads exactly as they did in 8.3.3, and
  the first packet re-anchors them.
- The Next Visible Pass chart now stands exactly as the station drew it
  -- the dot at the culmination, under the pass it names -- until the
  first loop packet arrives, normally a second or two after the page
  loads, and for as long as the feed stays down if it does not come at
  all.  8.3.3 hid the dot of an already-finished pass before any
  packet had landed; it no longer does, because the dot has no position
  to move to until the feed supplies one, and the page keeps no clock
  of its own to judge with.  Once the first packet is in, the verdict
  and the sweep are as they were in 8.3.3.
- Internal simplification behind all of the above: the clock-freshness
  test, the clock that could switch source, and the one-way pass-ended
  latch that policed that switch are all gone -- three functions and a
  piece of remembered state -- because there is no longer a second clock
  for them to guard against.  What replaces them is one clock and a
  stopwatch.  No configuration change, no new fields.

8.3.3 (2026/08/15)
------------------
- The Next Visible Pass chart's sweeping dot leaves the chart when the
  pass ends, instead of jumping backwards up the arc it has just ridden.
  At the set instant the dot was put back where the almanac drew it --
  the culmination, mid-arc -- and stayed there, beneath a header still
  naming the pass that had finished, until the next chart arrived up to
  five minutes later.  The dome did the right thing at the same instant
  (its mark disappears and the roster rolls to the next pass), so the
  two panels disagreed for the whole of that window.  The page was
  judging the chart against the loop feed's next_visible_pass, which
  rolls on to the FOLLOWING pass moments after this one sets; it now
  judges it against the chart's own rise and set, which weewx-skyfield
  2.3.2 writes on the pass arc (data-rise/data-set), so past the set the
  mark and its name label hide together, as they do on the dome, whether
  or not the page was open when the pass ended -- a page loaded in the
  gap before the next chart comes up with the mark already gone.  The
  arc, the header and the rest of the chart stand until the next chart
  replaces them.  On an older weewx-skyfield the chart carries no times
  of its own and the page falls back to the feed's window and 8.3.2's
  judgement of it -- the dot returns to its drawn place at set (its name
  label now leaves with it when the dot dips below the rim, which 8.3.2
  left standing).  Found in a live capture of NOAA-21's
  2026-08-15 pass, at the 02:58:35 set instant exactly.

8.3.2 (2026/08/15)
------------------
- ACTION: the sky dome's star field advances again on stations whose
  units are not the defaults.  The dome fragments are spaced across the
  archive interval, which the templates read as $current.interval.raw --
  a value delivered in whatever unit the report's group_interval asks
  for.  A station carrying `group_interval = hour` reports a five-minute
  interval as 0.0833, int() takes that to 0, and EVERY fragment renders
  empty, slot 0 included: the open page keeps the sky it was generated
  with for ever, the sun and planets go on moving across it, and nothing
  appears in the log because nothing failed.  Both templates now read
  the interval in seconds explicitly and round rather than truncate (the
  conversion is floating point, and 299.99988 would have cost the set a
  slot), with a fallback if it ever comes back non-positive.  This is the
  original fault behind Jacques Terrettaz's issue #4 -- he read the
  templates on his own station and found it.
- The satellite rosters keep rolling through a frozen dome.  8.3.1's
  freeze took them with it -- both the next-pass table under the dome and
  the visible-pass table beside the chart -- because the code that writes
  their countdown lines sat inside the dome's own render.  A station
  whose fragments stopped serving got a roster stuck on one pass beside a
  countdown chip that went on ticking, the two contradicting each other
  about the same satellite.  The rows are pure loop-feed arithmetic and
  now live outside the dome entirely, which is what the 8.3.1 notes
  already claimed.
- A frozen dome shows the sky the almanac drew.  8.3.1 froze the marks
  wherever the last nudge left them, which on a page restored from cache
  could be, most of the way across an hours-old sky -- and a body the
  live layer had HIDDEN for setting since the backdrop was drawn stayed
  hidden, so the plate could show a daytime sky with no sun in it.  Every
  mark now goes back to the backdrop's own geometry as the freeze
  engages.
- A dead loop feed no longer defeats the freeze.  The backdrop's age is
  judged against the station's clock, which the loop packets carry -- so
  when the feed stops, that clock stops, the backdrop can never be called
  stale, and 8.3.1 went on drawing bodies at their last known place while
  the star field behind them kept advancing: the same lie with the two
  inputs swapped.  Whichever input dies now, the marks return to the
  backdrop's geometry and the plate stays internally honest.  No second
  line under the panel: the LIVE badge already carries the feed's fault.
  A STALLED feed counts as a dead one: the commonest failure is not a
  failed fetch but weewx-loopdata stopping while the web server goes on
  serving the last file, so every poll succeeds and carries the same
  json.  A repeat of a packet already seen is not news, and does not
  keep the page believing its feed is alive.
- An empty fragment has its own reason in the frozen line ("dome-svg.txt
  is empty").  8.3.1 called it "not a sky fragment" -- the words for
  garbage -- when emptiness is sometimes by design (a slot beyond the
  archive interval) and sometimes means the station is writing no
  backdrop at all.  Naming the file is what tells the two apart.
- The line names the fragment that actually failed.  It is usually a
  numbered slot -- dome-svg-3.txt -- and 8.3.1 hardcoded dome-svg.txt, so
  a deploy that dropped only the numbered fragments sent the reader to
  the one file being served perfectly.
- The line waits until the page has actually asked.  "Nothing newer has
  arrived" is a claim about the station, and 8.3.1 could make it within
  the first second, before any refetch had returned -- a page restored
  from cache accused a station it had not yet spoken to.
- The frozen line's no-fault wording is plainer: "no newer backdrop has
  arrived" states what the page sees rather than accusing the station of
  not generating one.
- A hung server is reported as a hung server.  8.3.1's dome fetch wired
  ontimeout but never set a timeout, so a connection that was accepted
  and never answered left the request hanging: no error was recorded, the
  line fell back to the no-fault reason, and a dead request piled up
  every minute.  Thirty seconds now -- a rendered fragment is about
  140 KB, and a tighter budget failed every refetch over a slow mobile
  link -- and "no response" when it expires.  The loop-data poll
  has carried the mirror-image hazard since long before this release --
  its timeout was set BEFORE the request was opened, which older engines
  reject by throwing, inside a try whose catch would have swallowed it
  and left the page never going live at all.  Both are now set after
  opening.
- Every way a page comes back to life refetches the sky.  8.3.1 covered a
  tab returning to the front; the back button restoring from the
  browser's cache raises no visibility change at all, and neither does an
  OS suspend with the tab already in front -- the second is caught now by
  noticing that a one-second tick did not fire for two minutes.  A page
  also refetches once at load, so HTML served from a cache corrects
  itself at once instead of standing on a stale sky until the first
  minute boundary.
- A page coming back from sleep keeps its few seconds' grace even when
  the overdue interval, rather than the wake itself, sends the fetch --
  8.3.1 granted it only on the path that fetched, which is usually not
  the one that runs first.  And neither that grace nor a fetch in flight
  now retracts a line already standing: 8.3.1 could blank the
  explanation under a dome that never moved.
- One refetch at a time.  On resume the overdue interval and the wake
  both came due and each sent its own; 8.3.1's never-step-backward guard
  hid the collision rather than preventing it.
- ALTERING REPORT TIMING IS NOT SUPPORTED, and the manual now says so.
  The dome backdrops are written by the report cycle and the open page
  refetches them every minute; a report_timing that makes reports run
  less often than the archive interval leaves the page holding a sky
  older than it will draw marks over, so the dome freezes and says so.
  From the browser a deliberately slow report and a stopped station look
  exactly alike.  Lengthen the archive interval instead: the page follows
  that on its own.
- Every reason in the frozen line goes through the translation fallback,
  so a key that drifts from its source renders English rather than
  "undefined".
- The version log line is guarded where it claimed to be: the skin dict
  is now read inside the guard rather than at the call site, so a
  generator without one cannot take the page down.
- The French translation is reviewed in full by native speaker Jacques
  Terrettaz -- this skin's own strings included -- with his corrections
  to the roster's motion line ("s'eloigne a 28 km/s") and to the
  satellite pass strings ("culmine a 19 degrees").  The reference
  dictionary gains a translators' note that the pass sub-line's {rise},
  {culm} and {set} are compass points rather than times, a trap the other
  eight languages had open.
- Found by seven code reviews -- of 8.3.1, five of this change, and of
  the same machinery ported into another skin -- and by Jacques
  Terrettaz, who found the one that mattered by reading the templates.

8.3.1 (2026/08/15)
------------------
- A sky dome whose backdrop stops arriving now freezes and says so.  The
  star field and constellation figures are refetched once a minute; when
  those fetches stop landing the page used to keep the last good sky and
  go on nudging the sun, moon, planets and satellites across it, so the
  error grew at 15 degrees an hour with no bound and nothing on the page
  said a word.  Once the backdrop is three report cycles behind, the
  whole dome freezes -- marks and satellites together, since a satellite
  flying over a motionless star field is the lie this prevents -- and a
  line under the panel gives the reason.
- The reason names the fault, not just the symptom: an HTTP status when
  the fragments are not being served, "not a sky fragment" when what
  comes back is empty or unreadable, "no response" when nothing answers,
  and "no newer backdrop is being generated" when the fetches succeed and
  the station has simply stopped writing new ones -- the case no status
  code could ever reveal.  The line links to the manual's new
  "The star field is frozen" troubleshooting entry.
- The backdrop's age is judged by the STATION's clock, which the loop
  packets carry, not the viewer's: a browser clock an hour out can no
  longer freeze a perfectly healthy sky.  A dead loop feed therefore
  never raises the line -- the LIVE badge already carries that fault, and
  the dome's marks stop by themselves.
- Nothing else on the page is affected.  The Geocentric dial, the roster
  and the countdown chips stand on the loop feed, not on the backdrop,
  and go on ticking through a frozen dome.
- A page coming back from a closed laptop or a background tab now
  refetches the backdrop at once instead of waiting for the next minute
  boundary.  The timers stop with the machine, and on the way back the
  loop feed catches up within its two seconds while the sky did not --
  up to a minute of live marks moving over an hour-old star field, and,
  with the change above, a frozen line accusing a station that is doing
  nothing wrong.  The line is held for a few seconds while that fetch is
  in flight.
- The weewx log finally names this extension: "Celestial version is
  8.3.1.", at the first report that renders the page after a restart --
  and again if the version changes, so that from 8.3.1 on, a skin
  upgraded under a running weewxd announces itself at the next report
  cycle rather than staying quiet until somebody restarts.  Never once
  per cycle.  With no service since 7.0 nothing of this extension's ran
  at startup, so the log -- the first place anyone looks when a station
  misbehaves, and the first thing an issue report needs -- never named it
  at all.  The version comes from the skin that actually rendered the
  page, not from a file elsewhere claiming to be installed.
- Six new [Texts] strings (the line, its four reasons, and the link
  beside them), complete in all nine languages.
- Reported by Jacques Terrettaz (issue #4).

8.3 (2026/08/14)
----------------
- The page comes in light as well as dark.  A new report option --
  theme = dark | light | auto, beside lang in [[CelestialReport]] and
  NOT inside [[[Extras]]] -- puts the page on a paper-atlas plate, or
  follows the sun: light while it is up, dark once it sets, flipping
  within one archive interval.  dark is the default and is the page
  exactly as it was, so upgrading changes nothing until you ask.
- The WHOLE page changes together.  The sky dome and the Next Visible
  Pass chart are weewx-skyfield's drawings, and on a light page they are
  rendered on that extension's matching paper palette rather than left as
  a night rectangle inside a light page.  Every color the page draws
  itself is weewx-skyfield's light palette copied in, the same way the
  night values already were, so one page never shows two shades of one
  thing.  Needs weewx-skyfield 1.15 or later (2.2 for its own contrast
  pass); without weewx-skyfield the page has no charts to match and
  stays dark whatever the option says.
- The sun, the moon and Venus are drawn differently on paper rather than
  merely recolored: pale by identity, they measure 1.5, 1.4 and 1.3 to 1
  as fills on a white panel, so each takes a darker edge in its own
  color -- the outline of its dot, of its dashed below-horizon shape, of
  its motion trail, and a ring inside its roster chip.  Proxima Centauri,
  which wears the moon's silver, takes that edge color as its own.
- The plate is settled when the report is generated, not in the browser.
  The dome and the pass chart arrive as SVG with their colors already
  inside them and the page refetches them as it runs, so there is nothing
  for a browser-side toggle to switch and the page does not follow the
  viewer's operating system.  Both refetched fragments are rendered on
  the page's own palette, resolved from the page's generation instant, so
  a refetch can never land a night dome in a light page.  On theme = auto,
  where a report cycle really does cross sunrise, each backdrop declares
  the plate it was drawn on and a page still wearing the other one
  reloads itself once per flip -- so the flip reaches a page left open
  overnight within a minute, instead of waiting for someone to press
  reload.  A page that comes back still disagreeing (a cached copy) wears
  the stale plate rather than reloading again.
- A misspelled theme costs the plate and nothing else: the page renders
  whole on the night plate rather than losing its panels -- and says so
  in the log, naming the three valid values, so the mistake is visible
  instead of silently dark for ever.

8.2 (2026/08/14)
----------------
- The Geocentric dial gets its grid back.  Its rings, ticks and rim were
  drawn in the color of a section border, on the panel surface that
  border surrounds: 1.2 to 1.4 to 1 against their own background, which
  is present, correct and invisible.  They now have a color of their
  own -- weewx-skyfield 2.2's, so the dial and the sky dome still read
  as one instrument -- and the outer decade rings, the faintest thing
  on the dial, come up to the same weight skyfield gives its altitude
  rings.  The dots were never the problem; what was missing was the
  armature they are placed against, and a dial without one reads as
  washed out.
- Below the horizon is still dim, but no longer a smudge.  After dark
  most of the dial is below the horizon, so most of the dial was
  wearing that dim: a body's dashed outline is what actually carries
  it, and the outline is the body's own color at full strength, so the
  weight moves there -- the outline is half again as thick, the fill
  comes up a little, and the same lift reaches the moon's rim and the
  comet tails.  A body that is down still reads unmistakably as down.
- An hour-long motion trail now fades to something rather than to
  nothing.  The wake behind each dot ramped from full strength straight
  off zero, which spent its oldest twenty minutes below anything an eye
  can find; it fades from a visible floor instead, and its newest
  segment -- the one carrying the direction of travel -- is stronger.
- The sky dome's star and constellation names are easier to read, and
  Mars is one shade brighter everywhere on the page.  The names sit on
  the dome's gradient rather than on a panel, where the page's
  secondary-text color reached only 3.7:1; they have their own color
  now, and so do the dome's 30 and 60 degree ring marks.  This is the
  half of weewx-skyfield 2.2's contrast fix that lives in this skin's
  stylesheet -- the rest, including the altitude rings and the
  meridian/horizon cross that were drawn invisibly in the panel border
  color, arrives with the dome itself the moment 2.2 is installed.
  Mars is lifted here because the embedded dome carries its own copy of
  that color, and the two agree from weewx-skyfield 2.2 on; on a station
  still running 2.1 the dome keeps the darker Mars until it is upgraded.
  The constellation figures stay recessive on purpose.

8.1.2 (2026/08/13)
------------------
- The page generates again on WeeWX 5.2, this extension's stated
  minimum.  Since 7.2 it has taken its body names from the report's
  [Almanac] section, which WeeWX only began handing to the almanac in
  5.3; on 5.2 the report died while generating and the page never
  appeared at all.  The bodies now fall back to their capitalized
  English names (Moon, Jupiter, Proxima) when that section is out of
  reach, and nothing else on the page changes.  Translating body names
  still needs WeeWX 5.3 or later; the minimum stays 5.2.

8.1.1 (2026/08/12)
------------------
- A satellite pass row's whole-day countdown now counts CALENDAR days,
  so it can no longer contradict the date standing on its own line.  A
  pass 26 hours out, tomorrow morning, read "Jun 21 03:59 · in 2 days":
  the count was elapsed seconds rounded up, and rounding up calls
  anything still ahead of the clock a whole day.  Rounding down only
  moves the disagreement past midnight, so the count is now the
  difference between the two calendar dates, in the report's display
  timezone -- which is also right across a daylight-saving change,
  where 23 and 25 elapsed hours are each still one day.  Both the
  report-time first paint and the live layer are corrected, and they
  reckon identically.  Countdowns under a day are deliberately
  unchanged: "in 20 min" is what a go-watch reader wants, whichever
  side of midnight the pass falls on.  Jacques Terrettaz found this
  arithmetic in weewx-skyfield's countdown chips -- the morning of the
  2026-08-12 partial solar eclipse read "in 1 day" beside that day's
  own date (weewx-skyfield issue #6, fixed in its 2.1.2) -- and this
  page carried its own copy.  The countdown row's chips are not
  affected: a days-hours-minutes duration makes no claim about a
  calendar date.
- Everything else in this entry is documentation: nothing else in the
  shipped extension changes.
- The user manual is rebuilt and roughly doubled: twelve pages with a
  real sidebar and full-text search, at
  https://chaunceygardiner.github.io/weewx-celestial/.  Seven pages
  are new.  "Reading the page" is the key to the picture -- every badge
  state and what to do about it, the countdown chips (always-on versus
  the windowed guests, and why a chip you never see is not a fault),
  the dial's conventions and the comet vocabulary, the dome's marker
  states, and the fact that the dial faces east-RIGHT while the dome
  faces east-LEFT, deliberately, because a plan view and a view of the
  sky disagree about east.  "Troubleshooting" catalogues fifteen
  symptoms, each with the command that confirms it.  "How the page
  stays live" explains the three clocks behind the page for anyone
  deciding how much to trust a moving number.  "Fields reference" is
  now the one canonical list of what the skin reads, grouped by what
  each family feeds; "Satellites and comets" gathers the three
  weewx.conf edits each one takes, previously told in three places;
  and "Upgrading" splits the 7.x, 6.x and 5.x paths out of the
  installation page, which in turn gains a "Verify it" section.
- "The Geocentric in your skin" is rewritten as "In your own skin",
  covering the countdown row and the comet layer alongside the dial,
  and stating plainly why the sky dome and the Next Visible Pass panel
  are not a copyable interface: they are a private, in-step
  integration with weewx-skyfield whose internals change between
  releases.  The supported routes are named instead -- run the bundled
  page as it stands, or build on weewx-skyfield's own documented tags.
- The README is now a landing page: what the extension is, a three-step
  install, and a "where to find things" table pointing into the manual,
  rather than a second copy of it that could drift.  Two sections that
  had already drifted (the 6.x upgrade notes, still describing 7.0, and
  a weewx-skyfield version requirement that disagreed with the manual)
  are gone rather than fixed in place.
- The translation manual's reference dictionary is corrected: as
  shipped in 8.1 it printed one string the skin does not render and
  omitted one it does.  It is now identical to the skin's lang/en.conf,
  and a test keeps it that way.  The dictionary moves to a page of its
  own, so the translating instructions are no longer buried under 78
  strings; the Translations page also shows the Danish and Italian
  captures and links the other four.
- The Translations page now carries a per-language status table, and
  the translators' names with it: Christian (peters77) for the German
  and Jacques Terrettaz for the French -- both of whom reviewed the
  vocabulary these files share with weewx-skyfield, over in that
  extension -- beside Gert Andersen, who wrote the Danish entire.  The
  table states which review each file actually received, which
  sharpens what 7.2 and 7.7 claimed: the German and French are PARTLY
  reviewed -- the shared vocabulary yes, this skin's own strings (the
  page title, the badge states, the roster and countdown wording, the
  dome panel's eyebrow and install hint, the comet strings) not yet, in
  any language but Danish.  Each review is also DATED -- German as of
  7.2, French as of 7.7, Danish as of 7.8 -- because every one of these
  files has grown since it was read: 8.0 added the dome, satellite and
  pass strings and 8.1 the countdown row, the comets and the meteor
  showers, in every language, and an undated "reviewed" would claim a
  review of a file larger than the one anybody read.  Nothing about the
  shipped files changes; only the claim made for them.
- The test suite gains twenty-one documentation audits, so the manual
  can no longer disagree with the code on anything mechanical: the
  fields reference against the migrator's field set (entries and
  order), the per-satellite and per-comet patterns against the code
  that generates them, the countdown table against the event fields
  the skin actually reads, the translation dictionary against
  lang/en.conf and the language table against the shipped lang files,
  every internal manual link and anchor, and the report's
  options across three sources -- what skin.conf declares, what the
  templates read, and what the manual documents, including whether the
  documented defaults are the shipped ones.  The Configuration page's
  opening sample is checked against install.py's own config dict, since
  "what a fresh install writes" is a claim about a different file
  entirely.  A last pair checks the
  page furniture every page shares -- the in-body links back to the
  manual and the project, and the rule under them -- which is the one
  kind of drift no content audit can see.

8.1 2026/08/10
-----------------
- The installer now updates the [LoopData] [[Include]] fields line
  itself: weectl extension install appends the entries the page reads
  that are missing -- APPEND-ONLY, each one printed, existing entries
  never renamed, removed or reordered (an append cannot break another
  page consuming the same line), weectl's own weewx.conf backup made
  first, --dry-run honored.  Restart weewxd after installing so

4.0 Release 2026/07/05
----------------------
- ACTION REQUIRED (report tags): the embedded Skyfield report almanac has
  been removed.  Report tags such as $almanac.sunrise are now served by
  whatever almanac WeeWX has installed.  Install the weewx-skyfield
  extension (https://github.com/chaunceygardiner/weewx-skyfield) to keep
  Skyfield-quality tags, including named-star and hip_<n> tags such as
  $almanac.rigel.rise and $almanac.hip_57939.mag.  The
  replace_builtin_almanac option is gone; a leftover setting in the
  [Celestial] section of weewx.conf is ignored harmlessly.
- ACTION REQUIRED (loop fields): the deprecated pre-3.0 field names
  (Sunrise, MoonPhase, EarthMoonDistance, daySunshineDur, ...) are no
  longer emitted, as announced in 3.0.  A bundled utility migrates the
  [LoopData] [[Include]] [[[fields]]] line in one step -- renames the
  deprecated celestial fields in place, drops resulting duplicates, and
  appends the new 4.0 fields, never touching non-celestial fields:
      python -m user.celestial --migrate-loopdata-fields
          --config /path/to/weewx.conf --output /path/to/weewx.conf.migrated
  Compare and move into place (or use --in-place, which makes a backup
  first, or --print-fields-value for manual pasting).  Custom skins that
  read the old names from loop-data.txt must still be updated by hand;
  the full mapping is in the README.
- Loop fields are now cached by how often each can change: positions,
  distances and the moon's phase are recomputed every packet; rise/set,
  twilight and daylight fields once per local day; next
  equinox/solstice/full/new moon only when one passes.  A full recompute
  took ~270 ms on a Raspberry Pi 5 and previously ran every
  update_rate_secs; the steady-state cost is now ~20 ms per packet.
  Accordingly, update_rate_secs now throttles only the continuously
  varying fields, and the installed default is 0 (update on every loop
  packet, e.g. every 2 seconds with the Vantage driver).  An existing
  update_rate_secs setting in weewx.conf keeps working and may be set to
  0 to go live.
- New loop fields: moonPhaseIndex (0=new .. 4=full .. 7=waning crescent),
  moonWaxing (1 while waxing, else 0 -- exact where the index is coarse)
  and azimuth/altitude for all eight planets (mercuryAzimuth,
  mercuryAltitude, ... plutoAzimuth, plutoAltitude).  Measured steady-state
  cost on a Raspberry Pi 5: ~42 ms per packet (was ~20 ms).  Adding them to
  the [LoopData] fields list is only needed for the redesigned sample
  report's new visuals.
- The sample report is redesigned as a live "night-palette" page: a
  true-phase moon disc, countdown chips (next full/new moon, equinox,
  solstice), a day strip with twilight bands, rise/set ticks and a pulsing
  now-line that moves in real time, planets-now chips with per-body
  identity colors, and a responsive card layout (styles in the new
  celestial.css).  All previous data cells and their dual-source first
  paint (report-time almanac values + live loop data) are preserved.  To
  feed the new visuals, MERGE the fields listed in the README into the
  [LoopData] fields line (do not replace the line: it also carries the
  non-celestial fields other reports read).
- Sample report fixes: displayed times were hardcoded to
  America/Los_Angeles -- the station's timezone is now auto-detected at
  report generation time (via /etc/localtime), so every viewer sees
  station time with no configuration; a new time_zone Extras option can
  override (an IANA name, or 'browser' for the viewer's browser-local
  timezone).  The refresh_rate option is now honored (it was read but
  ignored, polling always at 2 s); a missing loop-data key no longer
  aborts the entire javascript update batch.
- The bundled sample skin still behaves as before for the data cells:
  report-time values render from the installed almanac when one with
  extended capabilities is available (weewx-skyfield or PyEphem), and
  javascript fills and updates every cell live from loop data either way.

----------------------
- Require Skyfield 1.47 or later (the first release with
  find_risings/find_settings, which rise/set computations use).  On an
  older Skyfield (e.g., Debian 12 packages 1.45), Celestial now logs an

  past the ephemeris' edge degrade the same way.

  after startup now degrades $almanac.hip_<n> tags to per-tag misses
  instead of aborting report generation (previously only a missing or
  unreadable file was handled).

  when a full hip_main.dat is installed (the records are identical),
  eliminating a full scan of the 118,218-record catalog at every WeeWX
  start.  hip_<n> lookups still prefer the full catalog.
- Internal hardening: $almanac.separation() computes each binder's
  coordinates with a single observation instead of two, and an
  unrecognized angle key now fails loudly instead of silently returning
  the elongation.

3.0 Release 2026/07/05
----------------------
- The loop fields have new names, following WeeWX's lowerCamelCase convention
  for observation names (Sunrise -> sunrise, MoonPhase -> moonPhase,
  EarthMoonDistance -> earthMoonDistance, etc.).  In addition, daySunshineDur
  and yesterdaySunshineDur are now daylightDur and yesterdayDaylightDur,
  because they measure daylight (sun above the horizon), not "sunshine
  duration" in the meteorological sense of measured bright sunshine.
  DEPRECATION: in 3.x, every value is written to the loop packet under BOTH
  its new and its old name, so existing [LoopData] fields lists and skins
  keep working unchanged.  The old names will be REMOVED in 4.0.  The full
  mapping is in the README ("Deprecated loop field names").  The bundled
  Celestial sample skin uses the new names as of 3.0.
- The loop packet's right ascension/declination fields (sunRightAscension,
  sunDeclination, moonRightAscension, moonDeclination) are now expressed in
  coordinates of date rather than J2000, the accepted convention for
  observed positions (and also that of PyEphem and of the report almanac's
  topo_ra/topo_dec); in 2025, right ascensions shift by roughly 0.4 degrees
  as a result.
- Where PyEphem and standard astronomical conventions differ, the report
  almanac follows the standard definitions (see "Differences from PyEphem"
  in the README): custom horizons are geometric (no refraction), matching
  the USNO twilight definitions; circumpolar/neverup use the same effective
  horizon as rise/set, so they always agree; hlongitude/hlatitude are true
  heliocentric coordinates for every body including the moon (PyEphem
  reports the moon's geocentric ecliptic longitude under this name), and
  for the sun they report Earth's heliocentric coordinates per the XEphem
  convention; $almanac.separation() takes (longitude, latitude) tuples and
  returns radians per the WeeWX 5.2 almanac API, and calls made with
  PyEphem Body arguments are passed through to PyEphem when installed.
- rigil_kentaurus now refers to Alpha Centauri A (HIP 71683, mag -0.01),
  matching PyEphem and the IAU designation.  It previously served Alpha
  Centauri B (HIP 71681, mag 1.35).
- New star: proxima_centauri (HIP 70890), the nearest star.  Unlike
  PyEphem, earth_distance and sun_distance work for stars, computed from
  the Hipparcos parallax (in astronomical units, like the planets).  A new
  loop field, earthProximaCentauriDistance, reports the distance in light
  years in every unit system (4.22 light years; miles/km are unreadable at
  that scale and the Hipparcos parallax is only good to ~0.3%).  The field
  is emitted only when the star catalog is enabled, and the sample skin
  displays it below the planet distances (add
  current.earthProximaCentauriDistance.raw to the [LoopData] fields line
  to keep it live-updating).
- The star names are no longer limited to PyEphem's catalog: every
  official proper name of the IAU Catalog of Star Names (the Working
  Group on Star Names' IAU-CSN list) that has a Hipparcos number is
  supported, e.g. $almanac.barnards_star.mag.  PyEphem's names remain
  as aliases -- 420 names in all, covering 412 stars.  Any other Hipparcos star can be addressed by catalog
  number ($almanac.hip_57939.rise); install a full hip_main.dat in the
  user directory to serve all 118,218 Hipparcos stars.  The bundled
  celestial_stars.dat excerpt grows from 48 KB to ~190 KB.
- The last PyEphem fallbacks are now computed natively: the moon's
  libration and selenographic colongitude (optical libration per Meeus
  ch. 53; the physical libration, at most 0.04 degrees, is neglected),
  Jupiter's central meridian longitudes (from the IAU rotation elements
  and light-time corrected geometry; PyEphem's values differ from the IAU
  definition by about 0.8 degrees), and Saturn's ring tilt (Meeus ch. 45).
  All in radians, like PyEphem's.  PyEphem is now only consulted for named
  stars when the star catalog is disabled, and for direct PyEphem body
  attributes this extension does not compute (e.g., moon.subsolar_lat).
- The bundled JPL ephemeris is renamed de421.bsp -> celestial_de421.bsp
  so that no other extension can claim the file (and remove it on its
  uninstall).  Skyfield does not care about the name.  NOTE: weectl does
  NOT remove files dropped from an extension's file list when upgrading,
  so after upgrading from 2.x, delete the orphaned 17 MB file yourself:
  sudo rm <weewx-root>/bin/user/de421.bsp
- Rise/set now honor the almanac's pressure/temperature: refraction is
  scaled from the standard 34 arcminutes, and WeeWX's documented
  pressure=0 idiom turns refraction off (these settings were previously
  ignored for rise/set; custom horizons remain geometric per the USNO
  twilight definitions).
- $almanac.separation() additionally accepts this almanac's own body
  binders ($almanac.separation($almanac.mars, $almanac.venus)), or a
  binder mixed with a coordinate tuple, computed natively; each binder is
  observed at its own almanac's time.
- The astronomical-unit conversion constants are now the IAU values
  (9.2955807e7 miles, 1.4959787e8 km per au); the old 9.296e7/1.496e8
  made every earth-to-body distance ~0.03% large.
- The sample skin degrades gracefully: its javascript reads loop fields by
  their new names but falls back to the old names, so an un-migrated
  [LoopData] fields list keeps the page updating; and when no extended
  almanac is available at report time (e.g., WeeWX before 5.2 without
  PyEphem, or replace_builtin_almanac = false without PyEphem), the page still
  generates with empty cells that the javascript fills in, as in 2.x.
- A malformed record in the star catalog now disables only that star,
  not the entire catalog.
- Replace WeeWX's built-in almanac (PyEphem or weeutil) for report generation.
  With WeeWX 5.2 or later, report tags such as $almanac.sunrise,
  $almanac.moon.transit, $almanac(horizon=-6).sun(use_center=1).rise and
  $almanac.next_full_moon are now computed with Skyfield and JPL's ephemeris,
  so generated reports show the same (more accurate) values as the loop
  packet fields.
- Physical attributes are also computed natively with Skyfield: $almanac.venus.mag
  (planets via Skyfield's Mallama/Hilton photometric models; sun, moon and Pluto
  via standard formulas), $almanac.venus.phase (percent illuminated),
  $almanac.sun.size/radius/radius_size (apparent angular size),
  $almanac.polaris.circumpolar, $almanac.venus.neverup,
  $almanac.venus.parallactic_angle and $almanac.sun.name.
- Add named star support (e.g., $almanac.rigel.rise, $almanac.polaris.circumpolar,
  $almanac.sirius.mag), on by default (set stars = false in the Celestial section
  of weewx.conf to turn it off).  Star data comes from celestial_stars.dat, a
  small excerpt of the Hipparcos Catalogue (ESA SP-1200, 1997; CDS VizieR I/239)
  installed with the extension.  All 115 star names of PyEphem's catalog are
  supported (multi-word names use underscores, e.g. $almanac.kaus_australis.rise).
- Anything Skyfield does not compute (e.g., the moon's libration, Jupiter's
  central meridian longitudes, stars when the catalog is not enabled) falls
  through to WeeWX's built-in almanac when PyEphem is installed.  Coverage was
  audited against the built-in almanac: with PyEphem installed, everything the
  built-in almanac can do continues to work; without PyEphem, all tags of the
  standard skins (and much more) work with Skyfield alone.
- Add replace_builtin_almanac field to the Celestial section of weewx.conf
  (default: true).  Set to false to leave report generation on the
  built-in almanac.
- The Celestial sample report is no longer empty at report generation time:
  every value on the page is now computed with the Skyfield almanac when the
  report is generated (formatted exactly as the javascript renders it), and
  the javascript then keeps the values updated from loop data on every loop
  record, as before.  So the page is now meaningful even when fetched
  without javascript (e.g., with curl).
- Add a pytest test suite (tests/test_almanac.py), including permanent parity
  audits against the built-in almanac.  Run with:
  /path/to/weewx-venv/bin/python -m pytest tests
- Bug fixes in the loop packet code:
  * daySunshineDur was wrong (or missing, due to a crash that was caught and
    logged) around the polar day/night transitions: on the first day of polar
    day (sun rises and never sets), on days when the sun is up at local
    midnight (it could go negative), and the sunset computation indexed the
    wrong array when checking whether the sun set.
  * Earth-to-body distances were reported in miles instead of kilometers for
    stations using the METRICWX unit system.
  * The skyfield timescale is now built once instead of on every update.
  * Fixed a typo (blufftone) that would crash the error handler if setting
    up the observer failed.
  * The WeeWX version check now compares major version numbers instead of
    strings (a string comparison would misjudge a hypothetical WeeWX 10).
  * Cleaned up type annotations (mypy is now clean), renamed a variable that
    shadowed a Python builtin, and fixed the --help usage text.
