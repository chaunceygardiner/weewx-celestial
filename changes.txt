weewx-celestial change history
------------------------------

9.0 2026/08/30
--------------
- ACTION ON UPGRADE: the sky dome's ten fragment templates
  (dome-svg.txt.tmpl and dome-svg-1..9.txt.tmpl), their shared
  dome-svg-frag.inc and pass-chart.txt.tmpl -- twelve files -- and the
  page's javascript include, realtime_updater.inc, are gone from the
  skin.  The files the templates wrote -- dome-svg.txt, dome-svg-1..9.txt
  and pass-chart.txt, exactly as before, so a page open across the
  upgrade keeps refetching successfully -- are now written by a
  generator, user.celestial_page.FragmentGenerator, listed in the skin's
  generator_list; the javascript is one static file, celestial.js (see
  below).  weectl only overlays files on an upgrade, so the old files
  stay in skins/Celestial on an upgraded station; nothing lists them any
  more, so they are inert -- but a later `weectl extension uninstall
  celestial` removes only the files it installed and leaves a directory
  it did not empty in place, so skins/Celestial would outlive the
  uninstall holding nothing but them.  Delete them once:
      rm /home/weewx/skins/Celestial/dome-svg*.txt.tmpl \
         /home/weewx/skins/Celestial/dome-svg-frag.inc \
         /home/weewx/skins/Celestial/pass-chart.txt.tmpl \
         /home/weewx/skins/Celestial/realtime_updater.inc
  (your SKIN_ROOT may differ).  An edit you made to one of them no
  longer applies.
- The page's panels start becoming something another skin can drop in,
  the way weewx-skyfield's $sky_page panels are.  This release's first
  step is the fragments: a new module, user.celestial_page, serves the
  page's $celestial search list (and $sky_page beside it, exactly as
  the celestial_sky shim does -- the shim stays for any skin that names
  it) and the FragmentGenerator, which writes the dome backdrops and
  the pass-chart fragment into the report's HTML_ROOT each cycle from
  the report's own almanac, theme and language.  A skin lists
  user.celestial_page.CelestialPanels among its search_list_extensions
  and user.celestial_page.FragmentGenerator in its generator_list and
  gets both; the bundled skin does exactly that and nothing more.
- The page's javascript is one static file, celestial.js, shipped
  beside sky.js and version-tagged in the page's URL like it, publishing
  one global (`celestial`) with one method, celestial.start(config).
  Everything it needs per report -- the [Extras] options, the station's
  latitude, the generation instant, the report's distance unit,
  language, body names, compass cardinals, [Texts] strings, satellites,
  comets, report name and loop-data file -- arrives in a config block
  the page generates ($celestial.config_script($almanac)) and nothing
  else in the script is per report.  Through 8.5 the whole script was a
  Cheetah include that baked those values into itself, which is why no
  other skin could run it; the page's behavior is unchanged, and the
  config's keys are a contract that only grows inside a major version.
  Two side effects worth knowing: the script no longer runs at window
  scope, so its names can no longer collide with the browser's
  (`history` once cost hours), and a name a report gives -- a report
  name or password containing `</script>` -- can no longer close the
  block early.
- The countdown row and the Geocentric panel -- the dial and its roster
  -- are the next two panels to become drop-in: the page renders them
  with $celestial.countdown_html($almanac) and
  $celestial.geocentric_html($almanac), and the three hundred lines of
  template that built them are gone.  What the page shows is unchanged
  (the markup is the same, indented differently) with one improvement:
  a comet added with --add-comet and no --name, and not named by the
  lang file, now reads in the roster as it does on the dial and its
  perihelion chip -- "Tsuchinshan Atlas", not "Tsuchinshan_atlas" --
  and every first
  paint (a chip's countdown, a body's distance and altitude, the
  install hint without an extended almanac) is still its own guarded
  read, so a lesser almanac costs that chip or that row, never the
  page.  New: a panel whose render fails outright is logged with its
  traceback and left out of the page, which the javascript then leaves
  alone; the rest of the page, and the rest of the live layer, carry
  on.  And a [Texts] translation that misspells a {placeholder} now
  paints it literally at generation, exactly as the javascript paints
  it live, so the first packet no longer changes what the page first
  showed (through 8.5 the cell rendered empty at generation and the
  placeholder appeared with the first packet).
- The sky dome, the Next Visible Pass chart, their two satellite
  rosters and the footer's credit are drop-in too: the page renders
  them with $celestial.dome_html($almanac), dome_roster_html,
  pass_html, pass_roster_html and footer_html, the page's plate comes
  from $celestial.theme_class, and the template is chrome plus calls
  -- the section headings, the two grids that put a chart beside its
  roster, the header.  The rosters are their own calls so another page
  can place them where it likes; pass_panel_hidden says whether the
  pass panel has anything to show at all (no chart and no roster row),
  which is when this page hides the section around it.  What the page
  shows is unchanged.  Every fragment -- the dome's wrapper on the page
  and each refetched one, and the pass chart, now wrapped the same way
  -- carries the report's theme beside its own set's plate, and the
  javascript judges the theme = auto flip by that -- against the theme
  the page was generated on, which the config block now carries --
  rather than by the fragment's plate, so a fragment set on a plate
  other than the page's (a night dome in a light page) is never
  mistaken for a flip and the flip itself is never missed -- not even
  by a page whose only fragment is the pass chart while no pass is in
  window: the empty chart now arrives in its wrapper too (a page still
  open from 8.x reads that as junk and keeps its chart, which a reload
  puts right).  A scalar written straight under [CelestialFragments] is
  refused, naming it, rather than ignored.  The panels beside the dome
  (the rosters, the Next Visible Pass) ask $sky_page.can_draw() --
  weewx-skyfield 2.3.4 or later -- whether the sky can be drawn at all;
  an older weewx-skyfield is asked the way the page always asked, by
  drawing the dome.  A registered almanac whose drawing still comes
  back empty gets its own line in the dome's place ("could not be
  drawn -- see the weewxd log") rather than the install hint.  If you
  are installing weewx-skyfield today, take 2.3.5: it adds nothing this
  page uses, but its install says what it is downloading while it
  downloads and leaves alone orbital elements the station already has
  and that are still current.  A weewx-skyfield
  whose dome_svg or pass_chart_html raises (its own methods are guarded
  and return empty, so this is an older one hitting a WeeWX
  incompatibility) still degrades the dome to its install hint and the
  chart to its hidden area, now with the traceback in the log.
- A page in another skin names the panels it embeds and the installer
  declares the satellite and comet fields for it: the report's stanza
  in weewx.conf carries `celestial_panels = countdown, geocentric,
  dome, pass` (those four are the panels), and the installer and the
  --add-/--remove-satellite/-comet verbs then keep that report's
  satellites and comets groups exactly as they keep the Celestial
  report's -- one writer -- and only the groups its panels read
  (satellites for the dome and the pass panel, comets for the
  Geocentric, both for the countdown row's pass and perihelion chips).
  On any report carrying the key those two group names are this
  extension's, replaced or removed wholesale on every run -- a group of
  your own belongs under another name -- and a group removed because no
  named panel reads it is reported as exactly that.  A key naming
  something that is not a panel costs that report its declaration and
  nobody else's: the installer and the verbs name it every run, and the
  key belongs on a report, never under [[Defaults]] or at [StdReport]'s
  top level (WeeWX merges both into every report), which is refused
  once, as the station's fault, in the installer's output and on every
  page whose report carries no key of its own.  Each panel also
  asks the installer's own question of the same weewx.conf when the
  page is generated, and a panel whose fields are not declared (the
  named panels between them read every group it reads, or they do not)
  carries a line before its root saying so, with a line in the weewxd
  log -- such a panel would otherwise first-paint and then never move,
  with nothing to say why; a panel named but not yet written (the key
  added and weewxd restarted without re-running weectl extension
  install, a satellite added to [Skyfield] by hand) carries a line
  saying what to run and to restart weewxd -- the installer's own dry
  run is what the page asks, against the configuration weewxd loaded
  at startup -- and the bundled Celestial page says the same when its
  own declaration is out of date (an 8.5 station whose [Skyfield] sets
  were edited by hand, or re-filled by a weewx-skyfield upgrade after
  --remove-satellite, will now be told); the log says it once per
  fault per cycle; the dome and the chart carry their panel's line,
  their rosters never do.  A key naming nothing is a
  statement (the report is a consumer whose page embeds no panel, and
  both groups go); a [[[celestial_panels]]] section where the line
  belongs is refused saying what a line looks like; a key under
  [[Defaults]] or at [StdReport]'s top level is refused on every report
  of another skin that carries none of its own, in the installer's
  output and on that report's page alike.  The fields that never change
  are a paste from the Celestial skin's own skin.conf into the
  consumer's.  A fragment set may declare a `directory` under
  HTML_ROOT, and a page may sit anywhere under HTML_ROOT: the page
  passes WeeWX's own $filename (its path under HTML_ROOT) to
  $celestial.config_script($almanac, $filename), the config block
  carries the page's route up to HTML_ROOT, and the javascript fetches
  every fragment from its set's directory there, wherever the page is
  and wherever the skin keeps its assets; a page that passes no
  $filename fetches relative to itself, as through 8.5.  A
  directory that could leave HTML_ROOT is refused, naming the set, one
  that cannot be made costs that set its files (named in the log) and
  no other set its cycle, and prefixes stay unique across sets whatever
  their directories.  A fragment fetch that comes back with an HTTP
  error or with something that is not a fragment earns one line in the
  browser console naming the URL asked.  Every panel's
  root element now carries data-celestial="<version>", the marker the
  consumer contract promises.  A minimal consumer skin lives under
  tests/fixtures -- its page in a subdirectory, using nothing but the
  public surface -- and is rendered through WeeWX's own report engine
  and driven in a real browser.
- The page names the fragment set it embeds -- dome_html($almanac,
  set='smartphone'), the same for pass_html -- and gets that set's
  first paint: its label scale, its plate and its file names, which the
  panel's own markup carries (data-dome-prefix on the dome's swap
  target, data-pass-fragment on the chart) so the javascript refetches
  the files the generator writes for that set.  No set means the set on
  the dome-svg prefix, which a skin declaring none has by default; a
  set the skin does not declare -- or no set on a skin that declares
  sets but none on the dome-svg prefix -- renders a line in the dome's
  place saying so and logs the name once per cycle, never the default.
  (Declaring any set replaces the default: a skin that adds one for a
  second page and keeps this page's own dome declares that one too,
  prefix = dome-svg.)
  So a declared set may take the dome-svg prefix at any scale or
  theme: the bundled page follows it.  A page with no dome or no chart
  refetches nothing for it.  A set on a plate other than the page's
  keeps its own label colors: the stylesheet styles a dome or chart's
  labels by the plate the fragment itself declares, not the page's.
- A page that embeds the panels without carrying the LIVE badge
  (#live-label, the page's own chrome rather than a panel) no longer
  throws once its expiration timer fires: the badge is written through
  the same guarded path as everything else the javascript paints.  Such
  a page simply has nowhere to report the feed's state, and stops
  polling after expiration_time hours with a reload as the way back.
- Display names the report controls -- a satellite's, a body's, a
  comet's, a shower's, from the [Almanac] section or the loop feed --
  and compass ordinals are markup-escaped where the panels and the
  javascript drop them into markup, as weewx-skyfield's own panels
  escape theirs.  A name carrying an ampersand or an angle bracket
  reads as written now; through 8.5 it was injected raw.
- One function now decides the staggered set's geometry -- how many
  backdrops an archive interval gets and how far apart -- and both the
  page's wrapper and the fragments read it.  Through 8.5 each carried
  its own copy of the arithmetic, and they disagreed once (fixed in 8.4).
- A skin can declare more than one fragment set in its skin.conf --
  [CelestialFragments], one [[subsection]] per set with its own prefix,
  label_scale and theme -- for two screen sizes, or a night dome inside
  a light page.  No section means the one set the page has always had.
  A set's theme takes dark, light or auto exactly as the report option
  does, resolved at the page's own instant, so auto flips when the page
  flips and never between; anything else is refused, naming the set.
  Two sets that would write the same file are refused at the first
  cycle, naming both, as are a label_scale that is not a positive
  number and a prefix that is not a plain file name.  A set costs no
  second satellite pass search: its plate is resolved from the report's
  one sky page.
- A fragment that fails to render is logged and its file left as it
  was, so the page keeps the sky it has; it is never written empty and
  never written with error text.  (The templates behaved the same way,
  through the CheetahGenerator; the generator now says which fragment
  failed and why.)  Without weewx-skyfield every fragment is written
  empty, as before, so the page's "is empty" line still points there.
- The generator's almanac is the page's: it is built by core WeeWX's
  own almanac search list, the code that builds $almanac for the
  template, so the two agree on every WeeWX version by construction --
  the 5.2 floor included.
- Tests: the 8.5 fragment templates are kept under tests/fixtures and
  rendered live beside the generator, which must write what they wrote,
  slot for slot, on both plates; the generator runs end to end into a
  scratch HTML_ROOT, with and without a database; its almanac is checked
  against the CheetahGenerator's own; and install.py's file list is
  checked against the tree in both directions.
- The stanza a fresh install writes into weewx.conf now explains itself:
  every option arrives with a comment saying what it does, and an option
  that merely picks a default arrives COMMENTED OUT, with the default
  shown -- refresh_rate and expiration_time of those already in the
  stanza, plus the three added below.  The value that governs is then
  the skin's, which every upgrade replaces, so a better default chosen
  in a later release reaches your station instead of only new ones.
  Uncomment one to pin your own value; what you set in weewx.conf still
  wins over the skin.
- Existing installations are untouched.  WeeWX fills in only what is
  absent from weewx.conf and never rewrites what is there, so nothing
  you have set changes, and the settings a previous install wrote stay
  exactly as they are.  Nothing to do on upgrade.
- Three options the stanza never mentioned now appear in it, commented
  out: lang and theme (the page's language and its dark/light plate) and
  time_zone.  They were discoverable only by reading the skin or the
  manual.  time_zone is the one exception to the rule above: its default
  is having NO value, which is what makes the page auto-detect your
  station's zone, so the line shown is an example rather than a default
  and the comment says so.
- loop_data_file and page_update_pwd stay live: neither is a default.
  The first is worked out for your station at install time, the second
  is a placeholder you are meant to replace.
- Documentation: the Configuration page prints the stanza as it is now
  written and says what the commented-out form means.  The password
  comment named the wrong URL parameter -- it is ?pageUpdate=<password>.
- Every class the panels render is prefixed cel- (cel-row, cel-roster,
  cel-caption), so embedding them in another skin cannot collide with
  that skin's own class names.  A real host skin names .row, .roster and
  .caption too, scoped more deeply than any selector this extension
  could write, so scoping loses in every load order and only prefixing
  settles it; class names are outside the published contract, and the
  DOM ids, which are inside it, are untouched.  The classes
  weewx-skyfield writes inside its own fragments keep its names, as does
  .skytip and the theme-dark/theme-light pair.
- The stylesheet is two files.  celestial.css is the PANELS, and it is
  what a skin embedding them loads; celestial-page.css is this report's
  own page -- the body, the header, the h1, the card a section draws,
  the footer, the document's color-scheme -- and only the bundled skin
  loads it.  Those rules name bare elements, so a page of another skin
  loading them was repainted whole, its titlebar and every unrelated
  section included.  A consumer must not load the second file.
- The dark and light plates are keyed on a class rather than on :root,
  so theme_class's answer can go on the container holding the panels as
  well as on the root element: that is how a night dome sits inside a
  light site.  theme-dark now selects something -- through 9.0 it
  matched no rule at all, the dark plate working only because :root
  carried it.
- The panels carry their own box model (scoped to the contract marker)
  rather than a bare `*` reset, and their sizes are em rather than rem,
  so one font-size on a consumer's container scales a whole panel.
- Documentation, from converting the first real consumer: the embed
  guide says to give the page's clock and badge ids OF YOUR OWN rather
  than reusing #last-update and #live-label (a skin with a #live-label
  of its own reused it, and two pollers painted the same cell in two
  dresses, two seconds apart); that a suite finding its fields by
  scanning script literals sees celestial.js's fallback key spellings,
  which are not fields to declare; that `set=` takes an UNQUOTED Cheetah
  variable, which is what a skin with two label scales needs and what
  every example until now failed to show; and that the config block's
  gen_ts is the instant the page was generated for.
- A skin that embeds the panels declares which ones in its OWN
  skin.conf (celestial_panels, at the top level), so installing it needs
  no edit to weewx.conf on any machine.  Which panels a page embeds is a
  property of its templates -- the same on every station, changing only
  when the skin changes -- and putting it in weewx.conf made bringing a
  consumer up a per-station chore, and a permanent one: the key was read
  only from there, so every station needed a hand edit and a second run
  of this extension's installer.  That is the chore weewx-loopdata 7.0
  existed to end for the fields that never change, reintroduced for the
  ones that follow the station's [Skyfield] sets.  A report's own stanza
  still overrides its skin, in the order WeeWX merges in, so a station
  can differ for one report without editing a skin it may not own; every
  report running a skin inherits that skin's key, which is what a second
  report on one skin wants.  Set in both places, the run says which file
  answered and warns when the two disagree.
- A consumer's own installer can declare its fields in one step, so
  installing the skin and restarting weewxd is the whole of it.  Its
  configure(engine) calls user.celestial.declare_page_fields(
  engine.config_dict, pending=self['config']) -- `pending` because
  weectl runs configure() BEFORE it injects the installer's config
  stanza, so on a fresh install the report does not exist yet and there
  would be nothing to declare under; the caller hands over the stanza it
  is about to have injected and weectl's own merge fills the rest in
  around it.  It is the mechanism this installer already uses for its
  own not-yet-existing report.  Order does not matter: install celestial
  first and the consumer's install writes the groups, install it
  afterwards and its own installer picks the report up.
- A consumer's groups are taken away when its skin is uninstalled.
  weectl has no uninstall hook, so a consumer skin cannot clean up after
  itself, and its groups would have been left for weewx-loopdata to
  evaluate every packet for panels that no longer exist.  A report that
  names no panels, carries those groups, and whose skin's skin.conf is
  ABSENT loses them on the next install or verb run, which reports it.
  Absent only: a skin.conf that merely cannot be read -- no permission,
  a mount that is not up, a half-written file, a syntax error -- is left
  alone and logged, because a skin that is gone is a statement while one
  that cannot be read is a question, and pruning on a question would let
  a permission bit look like an uninstall.
- Two fragment sets are refused for writing the same file only if they
  really would: the check follows `kind`, so a dome-only set no longer
  claims the pass fragment its prefix spells, nor a pass-only set the
  ten dome slots.  The first skin to use kind = dome / kind = pass hit
  this on its first run -- a dome-only set on the dome-svg prefix, whose
  pass fragment carries the legacy name pass-chart.txt, beside a
  pass-only set whose prefix was pass-chart -- and the report then wrote
  no fragments at all and every panel said its set was invalid.  One
  function now answers what a set writes, read by both the check and the
  generator, which is how the two came to disagree.  A set taking a
  prefix another set has is still refused, now as its own rule with its
  own message: a page that names no set finds its set by prefix.
- A dome or pass panel naming a set declared for the OTHER panel is
  refused, with the line a missing set gets and the reason in the log,
  rather than pointed at a fragment nothing writes: it would otherwise
  first-paint from the almanac and then fetch a 404 for ever, one line
  in the browser console and nothing on the page to say why.
- A fragment set says which fragments it writes: kind = dome, pass or
  both (the default, so nothing declared before this changes).  A skin
  with the dome on one page and the chart on another, at different label
  scales, declares a set for each, and without this each wrote the
  other's eleven files every cycle for a page that never asked.
- expiration_time = 0 means never expire, for a page in another skin
  that runs an expiry of its own; two regimes on one page is worse than
  either.  Through 9.0 that value armed a zero-delay timer and expired
  the page instantly.
- Documentation: the manual's "In your own skin" page becomes "Panels in
  your own skin", the embed guide -- the four things a skin arranges, the
  calls, a complete worked page, the two ids a consumer's own chrome
  owes the live layer, the stylesheet tokens (and the light plate's
  override rule), the contract, and what a panel says instead of drawing.
  The Fields reference prints which groups each panel reads;
  Configuration documents celestial_panels and [CelestialFragments];
  Troubleshooting gains the declaration and fragment-set faults;
  Translations says a consumer skin's [Texts] are its own.  The manual's
  tier table and the README name weewx-skyfield 2.3.4, which 9.0 uses
  where it is installed but does not require.


8.5 2026/08/26
--------------
- ACTION REQUIRED: weewx-loopdata 7.0 or later.  Upgrade it BEFORE
  installing this release: the installer refuses to run beside an
  older weewx-loopdata, or none, and says so.  The page's live values
  now reach it only through weewx-loopdata 7.0's per-report field
  declaration, which an older weewx-loopdata never reads -- the page
  would say BAD DATA for ever with nothing in any log to explain it.
  Only an install is checked: WeeWX runs an installed extension's
  loader for `weectl extension list` and `uninstall` too, and the page
  has to stay listable and removable after loopdata is gone.  Nothing
  else to do: install, restart weewxd.
- The page declares the loop-data fields it reads to weewx-loopdata
  itself, and reads its own entry of loop-data.txt.  The fifty fields
  that do not depend on your configuration ship in the skin's own
  skin.conf ([LoopData] [[fields]], grouped by panel); the satellite
  and comet fields, which follow your [Skyfield] [[Satellites]] and
  [[Comets]], are written by the installer under the report's own
  stanza -- [StdReport] [[CelestialReport]] [[[LoopData]]]
  [[[[fields]]]], one group each -- and rebuilt on every install so
  they track your sets (the installer defaults when there is no
  section to follow).  A second report of your own running the
  Celestial skin (another language, say) gets the same two groups.
  weewx-loopdata 7.0 writes each declaring report's fields under the
  REPORT's name, rendered in that report's own units, formats and
  [Almanac] names, so a display name set in [[CelestialReport]] now
  reaches the loop feed, and a Celestial report in German gets German
  shower names from the feed whatever language loopdata's sample
  report runs in.
- The installer no longer edits the [LoopData] [[Include]] fields
  line: a line left over from an earlier install is exactly as you had
  it, weewx-loopdata warns about it at startup, and it retires the
  line in a later release of its own.  It does count it: the entries
  on it that this page now declares itself -- the ~100 that 8.1-8.4's
  installers appended -- are evaluated twice per loop packet by
  weewx-loopdata 7.0 while the line stands, and the install says how
  many.  Trim this page's entries from it if no other page of yours
  reads them, or leave it for loopdata; do not add this page's fields
  to it.  --remove-satellite/--remove-comet likewise leave the line
  alone and say how many entries for the removed tag remain on it.
- A field of your own goes in a GROUP of your own, in the same
  [StdReport] [[CelestialReport]] [[[LoopData]]] [[[[fields]]]]
  section: never in the skin's skin.conf, which the next upgrade
  overwrites, and never in the satellites or comets groups, which the
  next install rebuilds.  Note that weectl extension uninstall
  celestial removes the report's whole stanza -- a group of your own
  and your [[[Extras]]] settings with it, as it always has -- so keep
  a copy if you uninstall, which the 6.x upgrade path does.
- The --migrate-loopdata-fields utility is gone with the line it
  edited.  A 5.x upgrade is now: uninstall, install weewx-loopdata
  7.0 and weewx-skyfield, install this, restart -- the manual's
  Upgrading page has the shortened sequence.
- --add-satellite/--add-comet and their inverses declare fields the
  same way: each rebuilds the report's satellites or comets group for
  the configured set -- the same code the installer runs -- instead of
  appending to or sweeping the fields line, and neither needs a
  fields line to exist any more.
- The badge reads BAD DATA -- check loop_data_file for a loop-data
  file that parses but carries no entry under this report's name (an
  older weewx-loopdata, or the report disabled), and the browser
  console names the missing key.
- The manual follows: Installation, Upgrading, the Fields reference
  (which now prints both halves of the declaration as shipped),
  Configuration, Satellites and comets, In your own skin,
  Troubleshooting and Translations.
- Drop-in over 8.4 once weewx-loopdata is 7.0: no configuration
  change of yours; the installer prints what it declared.

8.4 2026/08/24
--------------
- The installer works out where weewx-loopdata actually writes and
  points the page at it.  The page fetches loop_data_file, a URL
  relative to its OWN report's directory; weewx-loopdata writes
  loop_data_dir, a path relative to its TARGET report's directory.  Two
  different reports, so a shipped default can only be right for the
  layout it was chosen for -- and a page that asks the wrong URL says
  NO DATA (HTTP 404), which is the commonest trouble this extension
  has.  weewx.conf holds both halves, so the installer derives the
  value and writes it rather than shipping a guess.  The shipped
  default moves to ../loopdata/loop-data.txt -- where a stock
  weewx-loopdata writes -- for the station installed before
  weewx-loopdata, which leaves nothing to derive from.  A
  loop_data_file already in weewx.conf is never rewritten: it may be
  answering a web-server alias no installer can see, so a disagreement
  is reported and the change left to you.  Upgrading installs keep
  whatever they have.  A loop-data file written outside your reports
  tree (/dev/shm, or a directory of its own) is named as such and left
  to you as well -- a path on disk does not give the URL that serves
  it.
- The manual says where the loop-data file should live, and points at
  weewx-loopdata's manual for the how: the location is loopdata's
  setting, not this skin's.  The default -- inside your reports tree,
  where weewx-loopdata puts it -- works and is what most stations keep.
  This page's own half is documented here: with the file outside the
  reports tree, loop_data_file becomes the absolute URL your web server
  alias serves, and it is the one setting the installer cannot derive.
- The manual's countdown GIF is recaptured.  The old one was shot under
  8.1, when the chips ticked once a second; since 8.3.5 they step with
  each loop packet, so the caption had grown a paragraph of apology.
  The new capture is 8.3.5's behaviour, rolling through a real sunset:
  the chip counts to zero and turns into the next sunrise.
- A station whose console clock runs fast is no longer accused of
  writing no backdrops.  Its archive records are stamped ahead of its
  own loop packets, so every backdrop it serves depicts a time the page
  has not reached; the page refuses them -- it will not draw a sky from
  the future -- and the star field freezes.  That much is right, but the
  line under the panel read "no newer backdrop has arrived", which sent
  the reader looking for a report cycle that was running perfectly the
  whole time.  The line now names this case as its own, and the manual
  has a section for it.
- On an archive interval the fragment spacing does not divide -- 350
  seconds, say, against 60-second slots -- the station rendered a sixth
  backdrop every report cycle that no page could ever ask for, and the
  last 50 seconds of each cycle showed the slot before.  The set now
  counts what it writes.  Every standard WeeWX archive interval divides
  exactly and is unaffected.
- The Next Visible Pass chart stops rewriting its dot's hidden state
  twice a second through the minutes after a pass ends (8.3.5 fixed the
  same churn in the hours before one rises).
- Drop-in over 8.3.5; no configuration change.

8.3.5 (2026/08/17)
------------------
- The page's clock is the loop packet's own timestamp -- and, before the
  first packet, the instant the page was generated for.  8.3.4 carried
  the station's clock forward between packets on the browser's
  stopwatch; nothing does now, so the time shown always belongs to the
  data beside it.  A browser test proves a viewer clock half an hour
  wrong, either way, changes nothing on the page.
- The countdown chips and the satellite rosters repaint as loop packets
  arrive (every refresh_rate seconds) rather than once a second; the
  tick remains for the motion between packets.  A page with no working
  loop feed stands still, and the LIVE badge says why.
- The header's separate running clock is gone; the "updated" stamp
  beside it is baked at generation in 24-hour HH:MM:SS.
- The sky dome can no longer show a sky the station has not reached.
  The page worked out which backdrop to ask for from the backdrop it
  was holding, and for the first moments of every report cycle that one
  belongs to the cycle before -- so it named that cycle's late slot, and
  since a backdrop's filename carries a slot number and no cycle, the
  station answered out of the cycle it now held: a sky up to a cycle
  into the future, kept until the real time caught up to it.  The slot
  now follows from the station's clock and the archive interval alone
  (report cycles are generated for an archive record, so every cycle
  begins on an interval boundary), and a backdrop depicting a time the
  station has not reached is refused.  A laptop waking from sleep or a
  tab returning from the background steps to the right backdrop as soon
  as the loop feed catches up.
- The backdrop is fetched only when the sky is due to step -- when the
  slot the station's clock calls for is not the one already showing --
  instead of once a minute regardless.  A page in step with its station
  fetches nothing; a page whose station has stopped writing fetches
  nothing either, since its clock has stopped with it.  On an archive
  interval longer than ten minutes, where the slots are spaced further
  apart than the old once-a-minute refetch, most of those fetches
  returned a sky the page already had and were discarded.
- The Next Visible Pass chart no longer rewrites its dot's position and
  look once a second through the hours before a pass rises.  The chart
  stands as the station drew it, and is now restored once rather than
  continuously.
- Drop-in over 8.3.4; no configuration change.

8.3.4 (2026/08/16)
------------------
- The live page now reads one clock, and it is the station's.  Every
  instant the page reasons about -- a satellite pass's rise and set, a
  countdown chip's target, the roster's "overhead now", the header
  clock -- is written by the station, so the page no longer measures any
  of them against the viewer's own clock, which it has no reason to
  trust.  It asks the browser only how long something took, never what
  time it is.  A viewer whose clock was wrong could previously read
  every countdown off by the same amount, see the marks on the dial and
  the dome extrapolated up to two minutes from where they belong, and
  find a perfectly live feed labeled "120s ago"; all three now show
  the same page a correct clock shows.  Nothing is configured and
  nothing looks different on a machine whose clock is right.
- The clock is anchored on each loop packet's own timestamp and carried
  forward between packets; before the first packet arrives it is
  anchored on the page's own generation instant, so the countdown chips
  tick from the moment the page loads exactly as they did in 8.3.3, and
  the first packet re-anchors them.
- The Next Visible Pass chart now stands exactly as the station drew it
  -- the dot at the culmination, under the pass it names -- until the
  first loop packet arrives, normally a second or two after the page
  loads, and for as long as the feed stays down if it does not come at
  all.  8.3.3 hid the dot of an already-finished pass before any
  packet had landed; it no longer does, because the dot has no position
  to move to until the feed supplies one, and the page keeps no clock
  of its own to judge with.  Once the first packet is in, the verdict
  and the sweep are as they were in 8.3.3.
- Internal simplification behind all of the above: the clock-freshness
  test, the clock that could switch source, and the one-way pass-ended
  latch that policed that switch are all gone -- three functions and a
  piece of remembered state -- because there is no longer a second clock
  for them to guard against.  What replaces them is one clock and a
  stopwatch.  No configuration change, no new fields.

8.3.2 (2026/08/15)
------------------
- ACTION: the sky dome's star field advances again on stations whose
  units are not the defaults.  The dome fragments are spaced across the
  archive interval, which the templates read as $current.interval.raw --
  a value delivered in whatever unit the report's group_interval asks
  for.  A station carrying `group_interval = hour` reports a five-minute
  interval as 0.0833, int() takes that to 0, and EVERY fragment renders
  empty, slot 0 included: the open page keeps the sky it was generated
  with for ever, the sun and planets go on moving across it, and nothing
  appears in the log because nothing failed.  Both templates now read
  the interval in seconds explicitly and round rather than truncate (the
  conversion is floating point, and 299.99988 would have cost the set a
  slot), with a fallback if it ever comes back non-positive.  This is the
  original fault behind Jacques Terrettaz's issue #4 -- he read the
  templates on his own station and found it.
- The satellite rosters keep rolling through a frozen dome.  8.3.1's
  freeze took them with it -- both the next-pass table under the dome and
  the visible-pass table beside the chart -- because the code that writes
  their countdown lines sat inside the dome's own render.  A station
  whose fragments stopped serving got a roster stuck on one pass beside a
  countdown chip that went on ticking, the two contradicting each other
  about the same satellite.  The rows are pure loop-feed arithmetic and
  now live outside the dome entirely, which is what the 8.3.1 notes
  already claimed.
- A frozen dome shows the sky the almanac drew.  8.3.1 froze the marks
  wherever the last nudge left them, which on a page restored from cache
  could be, most of the way across an hours-old sky -- and a body the
  live layer had HIDDEN for setting since the backdrop was drawn stayed
  hidden, so the plate could show a daytime sky with no sun in it.  Every
  mark now goes back to the backdrop's own geometry as the freeze
  engages.
- A dead loop feed no longer defeats the freeze.  The backdrop's age is
  judged against the station's clock, which the loop packets carry -- so
  when the feed stops, that clock stops, the backdrop can never be called
  stale, and 8.3.1 went on drawing bodies at their last known place while
  the star field behind them kept advancing: the same lie with the two
  inputs swapped.  Whichever input dies now, the marks return to the
  backdrop's geometry and the plate stays internally honest.  No second
  line under the panel: the LIVE badge already carries the feed's fault.
  A STALLED feed counts as a dead one: the commonest failure is not a
  failed fetch but weewx-loopdata stopping while the web server goes on
  serving the last file, so every poll succeeds and carries the same
  json.  A repeat of a packet already seen is not news, and does not
  keep the page believing its feed is alive.
- An empty fragment has its own reason in the frozen line ("dome-svg.txt
  is empty").  8.3.1 called it "not a sky fragment" -- the words for
  garbage -- when emptiness is sometimes by design (a slot beyond the
  archive interval) and sometimes means the station is writing no
  backdrop at all.  Naming the file is what tells the two apart.
- The line names the fragment that actually failed.  It is usually a
  numbered slot -- dome-svg-3.txt -- and 8.3.1 hardcoded dome-svg.txt, so
  a deploy that dropped only the numbered fragments sent the reader to
  the one file being served perfectly.
- The line waits until the page has actually asked.  "Nothing newer has
  arrived" is a claim about the station, and 8.3.1 could make it within
  the first second, before any refetch had returned -- a page restored
  from cache accused a station it had not yet spoken to.
- The frozen line's no-fault wording is plainer: "no newer backdrop has
  arrived" states what the page sees rather than accusing the station of
  not generating one.
- A hung server is reported as a hung server.  8.3.1's dome fetch wired
  ontimeout but never set a timeout, so a connection that was accepted
  and never answered left the request hanging: no error was recorded, the
  line fell back to the no-fault reason, and a dead request piled up
  every minute.  Thirty seconds now -- a rendered fragment is about
  140 KB, and a tighter budget failed every refetch over a slow mobile
  link -- and "no response" when it expires.  The loop-data poll
  has carried the mirror-image hazard since long before this release --
  its timeout was set BEFORE the request was opened, which older engines
  reject by throwing, inside a try whose catch would have swallowed it
  and left the page never going live at all.  Both are now set after
  opening.
- Every way a page comes back to life refetches the sky.  8.3.1 covered a
  tab returning to the front; the back button restoring from the
  browser's cache raises no visibility change at all, and neither does an
  OS suspend with the tab already in front -- the second is caught now by
  noticing that a one-second tick did not fire for two minutes.  A page
  also refetches once at load, so HTML served from a cache corrects
  itself at once instead of standing on a stale sky until the first
  minute boundary.
- A page coming back from sleep keeps its few seconds' grace even when
  the overdue interval, rather than the wake itself, sends the fetch --
  8.3.1 granted it only on the path that fetched, which is usually not
  the one that runs first.  And neither that grace nor a fetch in flight
  now retracts a line already standing: 8.3.1 could blank the
  explanation under a dome that never moved.
- One refetch at a time.  On resume the overdue interval and the wake
  both came due and each sent its own; 8.3.1's never-step-backward guard
  hid the collision rather than preventing it.
- ALTERING REPORT TIMING IS NOT SUPPORTED, and the manual now says so.
  The dome backdrops are written by the report cycle and the open page
  refetches them every minute; a report_timing that makes reports run
  less often than the archive interval leaves the page holding a sky
  older than it will draw marks over, so the dome freezes and says so.
  From the browser a deliberately slow report and a stopped station look
  exactly alike.  Lengthen the archive interval instead: the page follows
  that on its own.
- Every reason in the frozen line goes through the translation fallback,
  so a key that drifts from its source renders English rather than
  "undefined".
- The version log line is guarded where it claimed to be: the skin dict
  is now read inside the guard rather than at the call site, so a
  generator without one cannot take the page down.
- The French translation is reviewed in full by native speaker Jacques
  Terrettaz -- this skin's own strings included -- with his corrections
  to the roster's motion line ("s'eloigne a 28 km/s") and to the
  satellite pass strings ("culmine a 19 degrees").  The reference
  dictionary gains a translators' note that the pass sub-line's {rise},
  {culm} and {set} are compass points rather than times, a trap the other
  eight languages had open.
- Found by seven code reviews -- of 8.3.1, five of this change, and of
  the same machinery ported into another skin -- and by Jacques
  Terrettaz, who found the one that mattered by reading the templates.

- A sky dome whose backdrop stops arriving now freezes and says so.  The
  star field and constellation figures are refetched once a minute; when
  those fetches stop landing the page used to keep the last good sky and
  go on nudging the sun, moon, planets and satellites across it, so the

  the fragments are not being served, "not a sky fragment" when what
  comes back is empty or unreadable, "no response" when nothing answers,

  packets carry, not the viewer's: a browser clock an hour out can no

  boundary.  The timers stop with the machine, and on the way back the

4.0 Release 2026/07/05
----------------------
- ACTION REQUIRED (report tags): the embedded Skyfield report almanac has
  been removed.  Report tags such as $almanac.sunrise are now served by
  whatever almanac WeeWX has installed.  Install the weewx-skyfield
  extension (https://github.com/chaunceygardiner/weewx-skyfield) to keep
  Skyfield-quality tags, including named-star and hip_<n> tags such as
  $almanac.rigel.rise and $almanac.hip_57939.mag.  The
  replace_builtin_almanac option is gone; a leftover setting in the
  [Celestial] section of weewx.conf is ignored harmlessly.
- ACTION REQUIRED (loop fields): the deprecated pre-3.0 field names
  (Sunrise, MoonPhase, EarthMoonDistance, daySunshineDur, ...) are no
  longer emitted, as announced in 3.0.  A bundled utility migrates the
  [LoopData] [[Include]] [[[fields]]] line in one step -- renames the
  deprecated celestial fields in place, drops resulting duplicates, and
  appends the new 4.0 fields, never touching non-celestial fields:
      python -m user.celestial --migrate-loopdata-fields
          --config /path/to/weewx.conf --output /path/to/weewx.conf.migrated
  Compare and move into place (or use --in-place, which makes a backup
  first, or --print-fields-value for manual pasting).  Custom skins that
  read the old names from loop-data.txt must still be updated by hand;
  the full mapping is in the README.
- Loop fields are now cached by how often each can change: positions,
  distances and the moon's phase are recomputed every packet; rise/set,
  twilight and daylight fields once per local day; next
  equinox/solstice/full/new moon only when one passes.  A full recompute
  took ~270 ms on a Raspberry Pi 5 and previously ran every
  update_rate_secs; the steady-state cost is now ~20 ms per packet.
  Accordingly, update_rate_secs now throttles only the continuously
  varying fields, and the installed default is 0 (update on every loop
  packet, e.g. every 2 seconds with the Vantage driver).  An existing
  update_rate_secs setting in weewx.conf keeps working and may be set to
  0 to go live.
- New loop fields: moonPhaseIndex (0=new .. 4=full .. 7=waning crescent),
  moonWaxing (1 while waxing, else 0 -- exact where the index is coarse)
  and azimuth/altitude for all eight planets (mercuryAzimuth,
  mercuryAltitude, ... plutoAzimuth, plutoAltitude).  Measured steady-state
  cost on a Raspberry Pi 5: ~42 ms per packet (was ~20 ms).  Adding them to
  the [LoopData] fields list is only needed for the redesigned sample
  report's new visuals.
- The sample report is redesigned as a live "night-palette" page: a
  true-phase moon disc, countdown chips (next full/new moon, equinox,
  solstice), a day strip with twilight bands, rise/set ticks and a pulsing
  now-line that moves in real time, planets-now chips with per-body
  identity colors, and a responsive card layout (styles in the new
  celestial.css).  All previous data cells and their dual-source first
  paint (report-time almanac values + live loop data) are preserved.  To
  feed the new visuals, MERGE the fields listed in the README into the
  [LoopData] fields line (do not replace the line: it also carries the
  non-celestial fields other reports read).
- Sample report fixes: displayed times were hardcoded to
  America/Los_Angeles -- the station's timezone is now auto-detected at
  report generation time (via /etc/localtime), so every viewer sees
  station time with no configuration; a new time_zone Extras option can
  override (an IANA name, or 'browser' for the viewer's browser-local
  timezone).  The refresh_rate option is now honored (it was read but
  ignored, polling always at 2 s); a missing loop-data key no longer
  aborts the entire javascript update batch.
- The bundled sample skin still behaves as before for the data cells:
  report-time values render from the installed almanac when one with
  extended capabilities is available (weewx-skyfield or PyEphem), and
  javascript fills and updates every cell live from loop data either way.

3.0 Release 2026/07/05
----------------------
- The loop fields have new names, following WeeWX's lowerCamelCase convention
  for observation names (Sunrise -> sunrise, MoonPhase -> moonPhase,
  EarthMoonDistance -> earthMoonDistance, etc.).  In addition, daySunshineDur
  and yesterdaySunshineDur are now daylightDur and yesterdayDaylightDur,
  because they measure daylight (sun above the horizon), not "sunshine
  duration" in the meteorological sense of measured bright sunshine.
  DEPRECATION: in 3.x, every value is written to the loop packet under BOTH
  its new and its old name, so existing [LoopData] fields lists and skins
  keep working unchanged.  The old names will be REMOVED in 4.0.  The full
  mapping is in the README ("Deprecated loop field names").  The bundled
  Celestial sample skin uses the new names as of 3.0.
- The loop packet's right ascension/declination fields (sunRightAscension,
  sunDeclination, moonRightAscension, moonDeclination) are now expressed in
  coordinates of date rather than J2000, the accepted convention for
  observed positions (and also that of PyEphem and of the report almanac's
  topo_ra/topo_dec); in 2025, right ascensions shift by roughly 0.4 degrees
  as a result.
- Where PyEphem and standard astronomical conventions differ, the report
  almanac follows the standard definitions (see "Differences from PyEphem"
  in the README): custom horizons are geometric (no refraction), matching
  the USNO twilight definitions; circumpolar/neverup use the same effective
  horizon as rise/set, so they always agree; hlongitude/hlatitude are true
  heliocentric coordinates for every body including the moon (PyEphem
  reports the moon's geocentric ecliptic longitude under this name), and
  for the sun they report Earth's heliocentric coordinates per the XEphem
  convention; $almanac.separation() takes (longitude, latitude) tuples and
  returns radians per the WeeWX 5.2 almanac API, and calls made with
  PyEphem Body arguments are passed through to PyEphem when installed.
- rigil_kentaurus now refers to Alpha Centauri A (HIP 71683, mag -0.01),
  matching PyEphem and the IAU designation.  It previously served Alpha
  Centauri B (HIP 71681, mag 1.35).
- New star: proxima_centauri (HIP 70890), the nearest star.  Unlike
  PyEphem, earth_distance and sun_distance work for stars, computed from
  the Hipparcos parallax (in astronomical units, like the planets).  A new
  loop field, earthProximaCentauriDistance, reports the distance in light
  years in every unit system (4.22 light years; miles/km are unreadable at
  that scale and the Hipparcos parallax is only good to ~0.3%).  The field
  is emitted only when the star catalog is enabled, and the sample skin
  displays it below the planet distances (add
  current.earthProximaCentauriDistance.raw to the [LoopData] fields line
  to keep it live-updating).
- The star names are no longer limited to PyEphem's catalog: every
  official proper name of the IAU Catalog of Star Names (the Working
  Group on Star Names' IAU-CSN list) that has a Hipparcos number is
  supported, e.g. $almanac.barnards_star.mag.  PyEphem's names remain
  as aliases -- 420 names in all, covering 412 stars.  Any other Hipparcos star can be addressed by catalog
  number ($almanac.hip_57939.rise); install a full hip_main.dat in the
  user directory to serve all 118,218 Hipparcos stars.  The bundled
  celestial_stars.dat excerpt grows from 48 KB to ~190 KB.
- The last PyEphem fallbacks are now computed natively: the moon's
  libration and selenographic colongitude (optical libration per Meeus
  ch. 53; the physical libration, at most 0.04 degrees, is neglected),
  Jupiter's central meridian longitudes (from the IAU rotation elements
  and light-time corrected geometry; PyEphem's values differ from the IAU
  definition by about 0.8 degrees), and Saturn's ring tilt (Meeus ch. 45).
  All in radians, like PyEphem's.  PyEphem is now only consulted for named
  stars when the star catalog is disabled, and for direct PyEphem body
  attributes this extension does not compute (e.g., moon.subsolar_lat).
- The bundled JPL ephemeris is renamed de421.bsp -> celestial_de421.bsp
  so that no other extension can claim the file (and remove it on its
  uninstall).  Skyfield does not care about the name.  NOTE: weectl does
  NOT remove files dropped from an extension's file list when upgrading,
  so after upgrading from 2.x, delete the orphaned 17 MB file yourself:
  sudo rm <weewx-root>/bin/user/de421.bsp
- Rise/set now honor the almanac's pressure/temperature: refraction is
  scaled from the standard 34 arcminutes, and WeeWX's documented
  pressure=0 idiom turns refraction off (these settings were previously
  ignored for rise/set; custom horizons remain geometric per the USNO
  twilight definitions).
- $almanac.separation() additionally accepts this almanac's own body
  binders ($almanac.separation($almanac.mars, $almanac.venus)), or a
  binder mixed with a coordinate tuple, computed natively; each binder is
  observed at its own almanac's time.
- The astronomical-unit conversion constants are now the IAU values
  (9.2955807e7 miles, 1.4959787e8 km per au); the old 9.296e7/1.496e8
  made every earth-to-body distance ~0.03% large.
- The sample skin degrades gracefully: its javascript reads loop fields by
  their new names but falls back to the old names, so an un-migrated
  [LoopData] fields list keeps the page updating; and when no extended
  almanac is available at report time (e.g., WeeWX before 5.2 without
  PyEphem, or replace_builtin_almanac = false without PyEphem), the page still
  generates with empty cells that the javascript fills in, as in 2.x.
- A malformed record in the star catalog now disables only that star,
  not the entire catalog.
- Replace WeeWX's built-in almanac (PyEphem or weeutil) for report generation.
  With WeeWX 5.2 or later, report tags such as $almanac.sunrise,
  $almanac.moon.transit, $almanac(horizon=-6).sun(use_center=1).rise and
  $almanac.next_full_moon are now computed with Skyfield and JPL's ephemeris,
  so generated reports show the same (more accurate) values as the loop
  packet fields.
- Physical attributes are also computed natively with Skyfield: $almanac.venus.mag
  (planets via Skyfield's Mallama/Hilton photometric models; sun, moon and Pluto
  via standard formulas), $almanac.venus.phase (percent illuminated),
  $almanac.sun.size/radius/radius_size (apparent angular size),
  $almanac.polaris.circumpolar, $almanac.venus.neverup,
  $almanac.venus.parallactic_angle and $almanac.sun.name.
- Add named star support (e.g., $almanac.rigel.rise, $almanac.polaris.circumpolar,
  $almanac.sirius.mag), on by default (set stars = false in the Celestial section
  of weewx.conf to turn it off).  Star data comes from celestial_stars.dat, a
  small excerpt of the Hipparcos Catalogue (ESA SP-1200, 1997; CDS VizieR I/239)
  installed with the extension.  All 115 star names of PyEphem's catalog are
  supported (multi-word names use underscores, e.g. $almanac.kaus_australis.rise).
- Anything Skyfield does not compute (e.g., the moon's libration, Jupiter's
  central meridian longitudes, stars when the catalog is not enabled) falls
  through to WeeWX's built-in almanac when PyEphem is installed.  Coverage was
  audited against the built-in almanac: with PyEphem installed, everything the
  built-in almanac can do continues to work; without PyEphem, all tags of the
  standard skins (and much more) work with Skyfield alone.
- Add replace_builtin_almanac field to the Celestial section of weewx.conf
  (default: true).  Set to false to leave report generation on the
  built-in almanac.
- The Celestial sample report is no longer empty at report generation time:
  every value on the page is now computed with the Skyfield almanac when the
  report is generated (formatted exactly as the javascript renders it), and
  the javascript then keeps the values updated from loop data on every loop
  record, as before.  So the page is now meaningful even when fetched
  without javascript (e.g., with curl).
- Add a pytest test suite (tests/test_almanac.py), including permanent parity
  audits against the built-in almanac.  Run with:
  /path/to/weewx-venv/bin/python -m pytest tests
- Bug fixes in the loop packet code:
  * daySunshineDur was wrong (or missing, due to a crash that was caught and
    logged) around the polar day/night transitions: on the first day of polar
    day (sun rises and never sets), on days when the sun is up at local
    midnight (it could go negative), and the sunset computation indexed the
    wrong array when checking whether the sun set.
  * Earth-to-body distances were reported in miles instead of kilometers for
    stations using the METRICWX unit system.
  * The skyfield timescale is now built once instead of on every update.
  * Fixed a typo (blufftone) that would crash the error handler if setting
    up the observer failed.
  * The WeeWX version check now compares major version numbers instead of
    strings (a string comparison would misjudge a hypothetical WeeWX 10).
  * Cleaned up type annotations (mypy is now clean), renamed a variable that
    shadowed a Python builtin, and fixed the --help usage text.
