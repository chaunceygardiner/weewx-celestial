weewx-celestial change history
------------------------------

8.1 2026/08/10
-----------------
- The installer now updates the [LoopData] [[Include]] fields line
  itself: weectl extension install appends the entries the page reads
  that are missing -- APPEND-ONLY, each one printed, existing entries
  never renamed, removed or reordered (an append cannot break another
  page consuming the same line), weectl's own weewx.conf backup made
  first, --dry-run honored.  Restart weewxd after installing so
  weewx-loopdata reloads the line.  The 8.1 additions it appends: the
  thirteen countdown-chip event fields (the sunset/sunrise and
  darkness-begins/-ends pairs, the equinox/solstice and Earth
  perihelion/aphelion pairs, the meteor
  shower peak and label, the supermoon, and the eclipse instant and
  kind -- the eclipse type is generation-time decoration from the
  report tag, no loop field needed)
  and six fields per comet, following your [Skyfield] [[Satellites]]
  and [[Comets]]
  (weewx-skyfield 2.1's installer defaults, Halley and Hale-Bopp, when
  there is no [[Comets]] section to follow).  Only pre-6.0 spellings
  stay manual -- renames deserve review, so the installer prints the
  tailored --migrate-loopdata-fields commands instead of applying
  them.  The comet layer and the
  shower/supermoon chips need weewx-skyfield 2.1; the sunset, darkness
  and satellite-pass chips light up on 2.0.  An almanac that cannot
  serve a field omits it from loop-data.txt (one weewxd log line per
  field) and the page hides that chip or layer; nothing else changes --
  the upgrade is otherwise drop-in.
- The Next Visible Pass chart's sweeping dot now flips between the solid
  sunlit dot and the hollow in-shadow ring live, from the same
  almanac.<satellite>.sunlit flag that drives the dome's marker -- the
  two panels stay in agreement when the satellite crosses the shadow
  line mid-pass.  8.0 kept the culmination's state for the whole ride
  (NOAA-21 culminating in shadow wore the ring from rise while the dome
  correctly showed the live shadow entry).  Outside the pass the chart
  still stands exactly as generated: the peak-instant portrait,
  culmination state included.
- Countdown central: a row of ticking countdown chips at the top of
  the page, each pure client arithmetic against an event-tier loopdata
  field -- computed once by the engine, cached until the event, zero
  cost at the one-second tick.  A countdown's precision follows its
  horizon: a day or more out it reads days-hours-minutes with the
  event's date beside it (seconds are noise at that range); inside the
  final day it becomes the ticking hh:mm:ss clock, where seconds are
  the point.  Always on: the soonest visible
  satellite pass ("ISS · appears in 00:41:12", ticking to zero, then
  "overhead now", rolling to the next pass the moment this one ends),
  sunset or sunrise -- whichever comes next, the chip flipping by
  itself at each event -- the next meteor shower's peak under its
  translated name with the moon's illumination AT the peak as the
  detail line (the fact that decides whether a shower year is worth an
  alarm), and astronomical darkness -- begins at the -18 degree
  sunset, ends at the -18 degree sunrise, whichever is next
  (stargazers care about both ends of the window; a high-latitude
  summer where -18 never comes hides the chip honestly).  Windowed
  guests appear only within ~30 days of the event, close enough to
  tick meaningfully: the next equinox or solstice, named by the season
  it begins ("autumn begins in 2d 04h 11m") -- the one event whose
  tick-to-zero is exact to the second -- Earth's perihelion or
  aphelion (early January and early July; minute-class extremum
  instants, weewx-skyfield 2.1 tags built on this page's ask), the
  next supermoon, the next
  eclipse visible from
  the station, and each configured comet's perihelion.  (weewx-skyfield's
  own page shows the perihelion as a dated chip up to a year out; the
  30-day window here is deliberate -- a ticking countdown wants a
  nearer horizon.)
- Comets ride the Geocentric dial: each [Skyfield] [[Comets]] entry
  places exactly like a planet -- compass azimuth, log Earth distance,
  below-horizon dimming, the same one-hour trail (on this dial the
  angle is azimuth, so a comet sweeps at the sky's diurnal rate like
  everything else) -- drawn as a diamond with a three-ray tail fanning
  away from the sun's own dial point, anti-sunward on the plan view.
  Solid diamond when the comet is naked-eye bright (magnitude 6.0 or
  brighter), the hollow inversion when fainter or when the Minor
  Planet Center row carries no magnitude parameters; the roster gains
  a row per comet, and the tap tooltip carries the live magnitude.  A
  comet the MPC has dropped serves nulls across its surface and the
  page renders absence -- no diamond, no row values, never the string
  "None".  The dome and the pass chart need nothing: their comet
  diamonds and shower radiants arrive inside weewx-skyfield's own
  fragments, and the live machinery passes both new mark shapes
  through untouched.
- --add-comet TAG=DESIGNATION [--name NAME] and --remove-comet TAG
  join the command-line utility, symmetric with the satellite verbs:
  one idempotent command for the three weewx.conf edits a comet takes
  (the [Skyfield] [[Comets]] entry, the six fields-line entries, the
  [StdReport] [[Defaults]] [[[Almanac]]] display name).  MPC
  designations validate (1P, 220P, "C/2023 A3" -- quote one with a
  space); satellites and comets share the almanac.<tag> namespace, so
  each family refuses the other's tags.  The migrator and the
  install-time fields hint follow [Skyfield] [[Comets]] exactly as
  they follow [[Satellites]]: a present-but-empty section is
  authoritative and appends nothing.
- All nine languages learn the new strings: the eclipse vocabulary,
  the perihelion label, the moon note and the radiant tooltip verbatim
  from weewx-skyfield's translations, the countdown chips' own wording
  (sunset, sunrise, darkness begins/ends, the four season-begins
  labels, supermoon, appears in)
  translated here; the [Almanac] sections gain Halley and Hale-Bopp
  display names and the twelve IMO meteor showers'.
- The Geocentric dial's caption reads "... trails show the last hour
  of motion · Hover or tap any mark for its coordinates."  Through 8.0
  the two sentences ran together with no separator (the joining "·" is
  template markup, so no translation changes).
- The tailored --migrate-loopdata-fields commands the installer prints
  now carry a PYTHONPATH=<weewx's location> prefix, so they paste and
  run on every install layout.  On a Debian/Red Hat package install
  WeeWX's own code lives in /usr/share/weewx, on the path only inside
  weectl, so the bare command 7.8-8.0 printed died with
  ModuleNotFoundError: No module named 'weewx' (reported by Gert
  Andersen).  The README and manual now show the package-install
  variant (cd /etc/weewx/bin, prefix PYTHONPATH=/usr/share/weewx)
  beside the venv commands for the migrator and the
  satellite/comet utilities.

8.0 2026/08/08
-----------------
- ACTION (only to light up the satellite layer): append the
  almanac.iss.* and almanac.tiangong.* entries to the [LoopData]
  [[Include]] fields line (the README has the full line;
  --migrate-loopdata-fields appends them for you, following your
  [Skyfield] [[Satellites]] so a customized set gets its own tags'
  entries instead) and run
  weewx-skyfield 2.0 with its default [[Satellites]].  Without them the
  page simply has no satellites; nothing else changes -- the upgrade is
  otherwise drop-in.
- weewx-loopdata 6.9 or later is now required (was 5.0): 8.0 depends on
  its almanac-field fixes, most visibly the event-cache expiry that
  rolls a satellite's next pass forward the moment it ends -- earlier
  loopdata serves the day's first pass until midnight, so the pass rows
  would read "just set" for hours.
- The installer tells you when that action is pending: weectl's
  configure hook compares the fields line with what the page reads
  (the bundled migrator run in memory as the oracle, so the check
  follows [Skyfield] [[Satellites]] exactly like the migrator) and
  prints the migration commands with concrete paths -- your weewx.conf,
  your bin directory, the running python -- when entries are missing or
  outdated spellings linger.  The review command it prints (and the
  docs now show) is a word-diff, git diff --no-index --word-diff: the
  fields line is one long comma-separated value, and a plain diff
  shows only two unreadable lines.  A hint only: the installer still never
  edits [LoopData] (weectl's conditional merge cannot append into
  another extension's comma-list value), it stays silent when the line
  is complete, and no failure in the check can fail the install.
- The page gains its second panel: the live sky dome.  The backdrop is
  weewx-skyfield's dome_svg -- the full Hipparcos star field, the
  constellation figures, sun, moon and planets -- embedded each report
  cycle through a new guard-only search list
  (user.celestial_sky.CelestialSkyPage serves $sky_page when
  weewx-skyfield is installed; any lesser almanac gets an install hint,
  never a broken page).  The open page steps the backdrop smoothly:
  each report cycle renders a staggered set of up to ten dome
  fragments (dome-svg.txt plus dome-svg-1..9.txt), spaced
  max(60 s, interval/10) across the archive interval, and the page
  refetches the slot covering the current minute -- a quarter-degree
  step instead of the whole cycle's rotation lurching at once (a
  five-minute step is plainly visible; watching a live pass proved
  it).  The fragments self-describe (timestamp, slot, spacing, count --
  the timestamp is the slot's own depicted time, and the slot number is
  what lets the walk recover the cycle base rather than stepping
  relative to whichever slot is showing, which zigzagged), so
  any archive interval gets full-cycle coverage unconfigured, and a
  late report cycle degrades to the freshest fragment available.
  Between steps the sun/moon/planet marks are nudged live at
  loop-derived rates through dome_svg's data-body hooks (new in
  skyfield 2.0; an older dome simply stands still between refetches).
  The dome is sky-chart orientation -- north up, east LEFT, as if lying
  on your back looking up -- deliberately opposite the Geocentric
  dial's map-convention plan view.
- Satellites, live.  With the new fields (above), the dome carries the
  layer that genuinely moves: the satellite marker -- dot and name --
  repositioned every second (wrap-aware azimuth extrapolation between
  loop packets), drawn whenever the satellite is up, its styling two
  composing signals: inside Earth's shadow the dot inverts to a hollow
  ring (the same convention as weewx-skyfield's dome marker), and a
  bright sky (sun at -6 degrees or above) dims dot and name -- so a
  dark-sky shadow exit reads as the flare it is, the ring snapping
  solid at full brightness, and solid-and-bright always means visible
  now, go look; beside
  it, a satellite roster -- each satellite's next pass of ANY kind,
  with a live countdown that rolls into "overhead now" during the
  show, the appears/peaks/disappears line, and a visible/not-visible
  tag from next_pass.visible, so the dome's dimmed daytime crossings
  are announced too -- with honest rows ("no pass in the coming
  week", "no usable orbital elements -- see the weewxd log") when
  that is the truth.  The satellite set follows
  [Skyfield] [[Satellites]] (enumerated through skyfield 2.0's public
  satellite_names()): every configured satellite gets its roster row
  and live tracking, given its fields -- the migrator appends fields
  for the [[Satellites]] set it finds in the weewx.conf it rewrites
  (the installer defaults, iss and tiangong, only when there is no
  [[Satellites]] section to follow; a present-but-empty section
  appends none, so a deliberately emptied set is never resurrected)
  and the README shows the per-satellite pattern for hand edits.  A loop feed without a satellite's
  keys (older skyfield, no [[Satellites]], an unmigrated fields line)
  hides that layer, never the page.  All new entries use pinned-unit
  spellings (the 7.5/7.6 doctrine), with bare-.raw read fallbacks for
  hand-written lines.  --in-place's backup suffix now carries the
  running version (.bak-celestial-8.0), so an 8.0 migration can never
  overwrite a preserved earlier backup.
- The Next Visible Pass panel, the page's third: skyfield 2.0's
  pass_chart_html embedded -- the whole sky as it will stand at the
  culmination of the soonest upcoming visible pass, the pass's arc
  dashed across it with rise and set times at the ends, under a dated
  head line -- beside a second satellite roster, each satellite's next
  VISIBLE pass, the ones worth stepping outside for.  One chart, one
  epoch, so the arc crosses the stars it will actually cross; the dome
  deliberately draws no arc (an undated
  future track on the now-sky read as tonight's).  During the pass
  itself the chart's moment is only minutes from now, and the page
  sweeps the satellite's dot live along the drawn arc.  When no
  visible pass is coming the chart area hides and the roster's honest
  rows say why (the whole panel hides only when no satellites are
  configured);
  the open page refetches the chart (pass-chart.txt, a third template
  in the report) every five minutes like the dome, so a completed
  pass's chart rolls over to the next pass by itself.
- Both rosters' head lines are composed at report time as date, time
  and countdown ("Aug 7 01:53 · in 3 h" -- the same idiom as
  weewx-skyfield's satellite chips and this page's own live layer),
  never the bare almanac rendering: its time-of-day-only form left a
  pass days away reading as today's whenever the live feed had nothing
  fresher to say (a satellite added minutes ago, a stalled feed).  The
  date's strftime format is a translatable [Texts] key ('%b %-d'),
  added to all nine languages verbatim from weewx-skyfield's.
- Tooltips work on touch screens.  Every mark on the dome and the pass
  chart carries a native SVG <title> tooltip, and browsers show those
  only on hover -- on an iPad they were simply dead.  The skin now
  ships weewx-skyfield 2.0's sky.js (copied verbatim, that repo the
  source of truth): a tap on or near a mark shows the same text as a
  floating chip, a tap on empty sky, Escape, scrolling or resizing
  dismisses it, and mouse users lose nothing -- the native hover
  tooltips still work, a click just pins the chip too.  Because this
  page is live, the updater dismisses an open chip whenever the dome
  or the pass chart swaps in a fresh fragment: a chip is a transient
  answer, never a stale overlay on a sky that has moved on.  The dome
  caption now reads "Hover or tap any mark for its coordinates.", in
  all nine languages, weewx-skyfield's translations verbatim.  The
  Geocentric dial joins in: its marks now carry the same tooltips
  (body name, live altitude or "below horizon", live distance -- the
  roster's own translated vocabulary, kept current by the same
  updater that moves the dots), served by the same tap machinery and
  the same caption sentence.
- New --add-satellite / --remove-satellite command-line utility.  A
  satellite beyond the installer's two takes three separate weewx.conf
  edits -- the [Skyfield] [[Satellites]] entry, its nineteen
  fields-line entries, the [StdReport] [[Defaults]] [[[Almanac]]]
  display name -- and --add-satellite TAG=NORAD (with an optional
  --name 'Display Name') makes them all in one command, one satellite
  per run; --remove-satellite TAG is the exact inverse.  Every edit is
  independently idempotent, so any mixed starting state converges: a
  satellite already configured per weewx-skyfield's manual keeps its
  entry and gains the fields, and re-running with a different number
  or --name updates that piece in place (the rename path).  Same write
  modes as the migrator: --output FILE (review the diff, original
  untouched) or --in-place (versioned backup first).  Removing an
  installer default (iss, tiangong) warns that the next weewx-skyfield
  upgrade re-adds its [[Satellites]] entry (weectl's conditional
  merge; re-run the removal afterwards), and removal never deletes the
  cached wxskyfield_sat_<norad>.tle element file.
- Three new translations, matching weewx-skyfield 2.0's: lang/it.conf
  (Italian), lang/no.conf (Norwegian Bokmål -- the file code is no,
  WeeWX's own code for Norwegian) and lang/sv.conf (Swedish), each
  complete (the completeness tests extend to them) and Beta until a
  native speaker reviews it.  The shared vocabulary -- body names,
  moon phases, compass points and all 88 constellation names -- is
  copied verbatim from weewx-skyfield's lang files, with the in-step
  test covering all three; lang = it (or no, or sv) on the report
  stanza switches the whole page, labels and live values alike.
- The dome, satellite and pass-chart strings are translated in all nine
  shipped languages, the shared vocabulary mined verbatim from
  weewx-skyfield's lang files, and the [Almanac] sections now carry the
  well-known satellite display names (iss = ISS, tiangong = Tiangong,
  hst = HST) so almanac.<sat>.label never falls back to title-case;
  only the dome panel's eyebrow, its install hint and the any-pass
  roster's four strings (its heading, its no-pass row, "visible",
  "not visible") are celestial's own wording.
- The Danish page title is now "Himlen over", Gert Andersen's original
  translation: 7.8 shipped "Himmellegemer over", a misreading of his
  message.
- The page-expiration timer clamps its delay to the browser's 32-bit
  ceiling (~24.8 days): an expiration_time over ~596 (the setting is
  hours) used to overflow the delay, which can make the page expire
  early -- even immediately -- instead of effectively never.

  pinned-unit spellings (almanac.next_full_moon.unix_epoch.raw,
  almanac.next_new_moon.unix_epoch.raw), completing 7.5's pinning: a

- A complete Dutch translation ships with the sample skin (Beta,
  awaiting native-speaker review -- corrections welcome): lang/nl.conf,
  its shared vocabulary -- body names, moon phases, compass points and
  all 88 constellations -- in step with weewx-skyfield's nl.conf (a test

  in the report.
- The --migrate-loopdata-fields utility now emits pinned-unit almanac
  entries for raw times and durations: almanac.sunrise.unix_epoch.raw,
  almanac.sun.visible.second.raw, and so on (weewx-loopdata 6.6
  documents the unit segment).  The old celestial loop fields always
  emitted epoch seconds and seconds regardless of report settings; an
  unpinned almanac .raw follows loopdata's target report converter, so
  a report with [Units] [[Groups]] overrides (e.g. group_deltatime =
  hour) would silently change a migrated field's meaning.  Pinned
  entries evaluate on every loopdata >= 5.0; users who already migrated
  need not re-run, but pages served by a unit-overriding target report
  should adopt the pinned spellings.

7.3 2026/07/28
--------------
- FIX: 7.2's page failed to generate under weewxd -- every cycle logged
  "cannot find 'Labels'" and the page went stale at whatever 7.1 had
  last written.  The header's hemisphere letters were read from a
  $Labels tag that does not exist in WeeWX's Cheetah search list (the
  render tests build their own search list, and it supplied a Labels
  entry core WeeWX never provides); they now come from
  $station.latitude[2]/$station.longitude[2], which core WeeWX computes
  from the same [Labels] hemispheres setting, lang-file aware, so the
  German letters are unchanged.  Install right over 7.2 and restart
  weewx; no configuration changes.

7.2 2026/07/28
--------------
The page is now translatable through WeeWX's own mechanisms (lang files,
[Texts]/$gettext, the [Almanac] section), and German ships with the skin.
No action required when upgrading: an untranslated report renders exactly
as before (English is the per-string fallback), and the loop-data field
set is unchanged.
- New skins/Celestial/lang/en.conf (the reference dictionary: every string
  the page renders, and nothing else -- a test keeps it exact in both
  directions) and lang/de.conf (complete German, native-speaker reviewed;
  body names, moon phases, hemispheres, compass ordinates and all 88
  constellation names are shared verbatim with weewx-skyfield's de.conf
  and a test keeps the two repos in step).  Select with lang = de in the
  report's section of weewx.conf (or [StdReport] [[Defaults]] to switch
  every German-shipping skin at once).
- The live javascript is translated too: body names (from the report's
  [Almanac] section, the same source as $almanac.<body>.label), compass
  cardinals (from the report formatter's ordinates) and every composed
  string (badge states, "receding"/"approaching", altitude and au cells,
  Proxima's light-year label) are resolved at report-generation time and
  fed to the script json-escaped, so the dial, roster and badge stay in
  the report's language between loop refreshes.
- The clock and last-update stamp now format per the report's lang
  (previously hardcoded en-US), and <html lang> reports it.
- The roster's body names now come from the almanac texts (capitalized --
  "Moon" where 7.1 showed "moon"; German nouns need the capital and the
  small-caps styling is unchanged).
- de.conf ships [Almanac] [[Constellations]] (all 88, keyed by IAU
  abbreviation) so constellation loopdata fields
  (almanac.<body>.constellation.label) and report tags arrive in German
  when this report is the loopdata target, even though the page itself
  does not currently render constellations.
- New user manual at https://chaunceygardiner.github.io/weewx-celestial/
  (the docs/ directory): home, installation/upgrading, configuration,
  building the Geocentric into your own skin, and translating.  The
  README and the manual link to each other.

7.1 2026/07/24
--------------
A failed loop-data fetch now says so on the page.  When the poll for
loop_data_file comes back as anything but the json -- the classic being the
web server's 404 page because weewx-loopdata writes outside HTML_ROOT (say
/dev/shm) with no alias serving it -- the LIVE badge now reads
"NO DATA (HTTP 404) -- check loop_data_file" (or "BAD DATA -- check
loop_data_file" for a 200 that isn't json); previously the only trace was a
JSON.parse error in the browser console and a silently dead page.  A
network-level failure or timeout shows OFFLINE (previously a blank badge).
A later successful poll rewrites the badge to LIVE as always.  New
headless-Chromium test covers the 404 case.

7.0 2026/07/23
--------------
ACTION REQUIRED when upgrading: (1) `weectl extension uninstall celestial`
before installing 7.0, as always.  (2) If `user.celestial.Celestial` still
appears under data_services in [Engine] [[Services]] (a 2.x leftover that
6.x tolerated with a stub), REMOVE it -- 7.0 deletes the stub and a stale
entry will keep weewxd from starting.  (3) Add
`almanac.proxima_centauri.az` and `almanac.proxima_centauri.alt` to the
[LoopData] [[Include]] fields line (the other 7.0 fields are already in
any 6.0 line; the no-longer-read 6.0 entries -- rise/sets, twilights,
ra/dec, equinox/solstice, moon_phase, moon_index, sun visible-time -- may
be kept for your own pages or trimmed).  The rewritten stylesheet needs no
action: CopyGenerator re-copies copy_once files on every report first-run
(the restart covers it), and the page now version-tags the celestial.css
URL so browsers refetch it after an upgrade instead of serving a stale
cached copy (which would bury the dial under unstyled ring discs).
- The sample skin is rebuilt around a single live panel, the Geocentric:
  Earth at the center, every body (sun, moon, planets, Proxima Centauri)
  placed by compass bearing (plan view, east right) and log distance,
  the moon at its true phase with a silver rim, below-horizon bodies
  dimmed and dashed, an hour of motion trail behind every dot, and a
  roster whose distance odometers tick between loop refreshes at each
  body's true radial rate (derived from consecutive loop packets,
  re-anchored on every refresh, frozen if the feed goes stale).
- Removed: the seven embedded weewx-skyfield SVG panels (sky dome, solar
  year, lunation, sun path, orrery, analemma, rise/set ribbons) and every
  almanac-table card -- they duplicated weewx-skyfield's own Sky page and
  plain almanac data any skin can render.  weewx-skyfield is the atlas;
  this page is the live instrument.  Also removed: the CelestialSkyPage
  search-list shim (nothing embeds $sky_page now) and the 6.x Celestial
  service stub.
- The footer credit is now generated truthfully for whatever almanac
  serves the page (full Skyfield/DE421/Hipparcos credit only when Proxima
  is served; generic extended-almanac and built-in-almanac renditions
  otherwise).
- The sample-report field set shrinks from 58 entries to 37 (az/alt/
  earth_distance per body, the moon-phase fields, current.dateTime.raw);
  the migrator appends the new set, including the two new Proxima
  position fields.  --in-place backups are named .bak-celestial-7.0.

6.0 2026/07/19
--------------
ACTION REQUIRED when upgrading: this release removes the loop-field
service.  Run `weectl extension uninstall celestial` BEFORE installing 6.0

`user.celestial.Celestial` in data_services and orphans the old

4.0 Release 2026/07/05
----------------------
- ACTION REQUIRED (report tags): the embedded Skyfield report almanac has
  been removed.  Report tags such as $almanac.sunrise are now served by
  whatever almanac WeeWX has installed.  Install the weewx-skyfield
  extension (https://github.com/chaunceygardiner/weewx-skyfield) to keep
  Skyfield-quality tags, including named-star and hip_<n> tags such as
  $almanac.rigel.rise and $almanac.hip_57939.mag.  The
  replace_builtin_almanac option is gone; a leftover setting in the
  [Celestial] section of weewx.conf is ignored harmlessly.
- ACTION REQUIRED (loop fields): the deprecated pre-3.0 field names
  (Sunrise, MoonPhase, EarthMoonDistance, daySunshineDur, ...) are no
  longer emitted, as announced in 3.0.  A bundled utility migrates the
  [LoopData] [[Include]] [[[fields]]] line in one step -- renames the
  deprecated celestial fields in place, drops resulting duplicates, and
  appends the new 4.0 fields, never touching non-celestial fields:
      python -m user.celestial --migrate-loopdata-fields
          --config /path/to/weewx.conf --output /path/to/weewx.conf.migrated
  Compare and move into place (or use --in-place, which makes a backup
  first, or --print-fields-value for manual pasting).  Custom skins that
  read the old names from loop-data.txt must still be updated by hand;
  the full mapping is in the README.
- Loop fields are now cached by how often each can change: positions,
  distances and the moon's phase are recomputed every packet; rise/set,
  twilight and daylight fields once per local day; next
  equinox/solstice/full/new moon only when one passes.  A full recompute
  took ~270 ms on a Raspberry Pi 5 and previously ran every
  update_rate_secs; the steady-state cost is now ~20 ms per packet.
  Accordingly, update_rate_secs now throttles only the continuously
  varying fields, and the installed default is 0 (update on every loop
  packet, e.g. every 2 seconds with the Vantage driver).  An existing
  update_rate_secs setting in weewx.conf keeps working and may be set to
  0 to go live.
- New loop fields: moonPhaseIndex (0=new .. 4=full .. 7=waning crescent),
  moonWaxing (1 while waxing, else 0 -- exact where the index is coarse)
  and azimuth/altitude for all eight planets (mercuryAzimuth,
  mercuryAltitude, ... plutoAzimuth, plutoAltitude).  Measured steady-state
  cost on a Raspberry Pi 5: ~42 ms per packet (was ~20 ms).  Adding them to
  the [LoopData] fields list is only needed for the redesigned sample
  report's new visuals.
- The sample report is redesigned as a live "night-palette" page: a
  true-phase moon disc, countdown chips (next full/new moon, equinox,
  solstice), a day strip with twilight bands, rise/set ticks and a pulsing
  now-line that moves in real time, planets-now chips with per-body
  identity colors, and a responsive card layout (styles in the new
  celestial.css).  All previous data cells and their dual-source first
  paint (report-time almanac values + live loop data) are preserved.  To
  feed the new visuals, MERGE the fields listed in the README into the
  [LoopData] fields line (do not replace the line: it also carries the
  non-celestial fields other reports read).
- Sample report fixes: displayed times were hardcoded to
  America/Los_Angeles -- the station's timezone is now auto-detected at
  report generation time (via /etc/localtime), so every viewer sees
  station time with no configuration; a new time_zone Extras option can
  override (an IANA name, or 'browser' for the viewer's browser-local
  timezone).  The refresh_rate option is now honored (it was read but
  ignored, polling always at 2 s); a missing loop-data key no longer
  aborts the entire javascript update batch.
- The bundled sample skin still behaves as before for the data cells:
  report-time values render from the installed almanac when one with
  extended capabilities is available (weewx-skyfield or PyEphem), and
  javascript fills and updates every cell live from loop data either way.

3.0 Release 2026/07/05
----------------------
- The loop fields have new names, following WeeWX's lowerCamelCase convention
  for observation names (Sunrise -> sunrise, MoonPhase -> moonPhase,
  EarthMoonDistance -> earthMoonDistance, etc.).  In addition, daySunshineDur
  and yesterdaySunshineDur are now daylightDur and yesterdayDaylightDur,
  because they measure daylight (sun above the horizon), not "sunshine
  duration" in the meteorological sense of measured bright sunshine.
  DEPRECATION: in 3.x, every value is written to the loop packet under BOTH
  its new and its old name, so existing [LoopData] fields lists and skins
  keep working unchanged.  The old names will be REMOVED in 4.0.  The full
  mapping is in the README ("Deprecated loop field names").  The bundled
  Celestial sample skin uses the new names as of 3.0.
- The loop packet's right ascension/declination fields (sunRightAscension,
  sunDeclination, moonRightAscension, moonDeclination) are now expressed in
  coordinates of date rather than J2000, the accepted convention for
  observed positions (and also that of PyEphem and of the report almanac's
  topo_ra/topo_dec); in 2025, right ascensions shift by roughly 0.4 degrees
  as a result.
- Where PyEphem and standard astronomical conventions differ, the report
  almanac follows the standard definitions (see "Differences from PyEphem"
  in the README): custom horizons are geometric (no refraction), matching
  the USNO twilight definitions; circumpolar/neverup use the same effective
  horizon as rise/set, so they always agree; hlongitude/hlatitude are true
  heliocentric coordinates for every body including the moon (PyEphem
  reports the moon's geocentric ecliptic longitude under this name), and
  for the sun they report Earth's heliocentric coordinates per the XEphem
  convention; $almanac.separation() takes (longitude, latitude) tuples and
  returns radians per the WeeWX 5.2 almanac API, and calls made with
  PyEphem Body arguments are passed through to PyEphem when installed.
- rigil_kentaurus now refers to Alpha Centauri A (HIP 71683, mag -0.01),
  matching PyEphem and the IAU designation.  It previously served Alpha
  Centauri B (HIP 71681, mag 1.35).
- New star: proxima_centauri (HIP 70890), the nearest star.  Unlike
  PyEphem, earth_distance and sun_distance work for stars, computed from
  the Hipparcos parallax (in astronomical units, like the planets).  A new
  loop field, earthProximaCentauriDistance, reports the distance in light
  years in every unit system (4.22 light years; miles/km are unreadable at
  that scale and the Hipparcos parallax is only good to ~0.3%).  The field
  is emitted only when the star catalog is enabled, and the sample skin
  displays it below the planet distances (add
  current.earthProximaCentauriDistance.raw to the [LoopData] fields line
  to keep it live-updating).
- The star names are no longer limited to PyEphem's catalog: every
  official proper name of the IAU Catalog of Star Names (the Working
  Group on Star Names' IAU-CSN list) that has a Hipparcos number is
  supported, e.g. $almanac.barnards_star.mag.  PyEphem's names remain
  as aliases -- 420 names in all, covering 412 stars.  Any other Hipparcos star can be addressed by catalog
  number ($almanac.hip_57939.rise); install a full hip_main.dat in the
  user directory to serve all 118,218 Hipparcos stars.  The bundled
  celestial_stars.dat excerpt grows from 48 KB to ~190 KB.
- The last PyEphem fallbacks are now computed natively: the moon's
  libration and selenographic colongitude (optical libration per Meeus
  ch. 53; the physical libration, at most 0.04 degrees, is neglected),
  Jupiter's central meridian longitudes (from the IAU rotation elements
  and light-time corrected geometry; PyEphem's values differ from the IAU
  definition by about 0.8 degrees), and Saturn's ring tilt (Meeus ch. 45).
  All in radians, like PyEphem's.  PyEphem is now only consulted for named
  stars when the star catalog is disabled, and for direct PyEphem body
  attributes this extension does not compute (e.g., moon.subsolar_lat).
- The bundled JPL ephemeris is renamed de421.bsp -> celestial_de421.bsp
  so that no other extension can claim the file (and remove it on its
  uninstall).  Skyfield does not care about the name.  NOTE: weectl does
  NOT remove files dropped from an extension's file list when upgrading,
  so after upgrading from 2.x, delete the orphaned 17 MB file yourself:
  sudo rm <weewx-root>/bin/user/de421.bsp
- Rise/set now honor the almanac's pressure/temperature: refraction is
  scaled from the standard 34 arcminutes, and WeeWX's documented
  pressure=0 idiom turns refraction off (these settings were previously
  ignored for rise/set; custom horizons remain geometric per the USNO
  twilight definitions).
- $almanac.separation() additionally accepts this almanac's own body
  binders ($almanac.separation($almanac.mars, $almanac.venus)), or a
  binder mixed with a coordinate tuple, computed natively; each binder is
  observed at its own almanac's time.
- The astronomical-unit conversion constants are now the IAU values
  (9.2955807e7 miles, 1.4959787e8 km per au); the old 9.296e7/1.496e8
  made every earth-to-body distance ~0.03% large.
- The sample skin degrades gracefully: its javascript reads loop fields by
  their new names but falls back to the old names, so an un-migrated
  [LoopData] fields list keeps the page updating; and when no extended
  almanac is available at report time (e.g., WeeWX before 5.2 without
  PyEphem, or replace_builtin_almanac = false without PyEphem), the page still
  generates with empty cells that the javascript fills in, as in 2.x.
- A malformed record in the star catalog now disables only that star,
  not the entire catalog.
- Replace WeeWX's built-in almanac (PyEphem or weeutil) for report generation.
  With WeeWX 5.2 or later, report tags such as $almanac.sunrise,
  $almanac.moon.transit, $almanac(horizon=-6).sun(use_center=1).rise and
  $almanac.next_full_moon are now computed with Skyfield and JPL's ephemeris,
  so generated reports show the same (more accurate) values as the loop
  packet fields.
- Physical attributes are also computed natively with Skyfield: $almanac.venus.mag
  (planets via Skyfield's Mallama/Hilton photometric models; sun, moon and Pluto
  via standard formulas), $almanac.venus.phase (percent illuminated),
  $almanac.sun.size/radius/radius_size (apparent angular size),
  $almanac.polaris.circumpolar, $almanac.venus.neverup,
  $almanac.venus.parallactic_angle and $almanac.sun.name.
- Add named star support (e.g., $almanac.rigel.rise, $almanac.polaris.circumpolar,
  $almanac.sirius.mag), on by default (set stars = false in the Celestial section
  of weewx.conf to turn it off).  Star data comes from celestial_stars.dat, a
  small excerpt of the Hipparcos Catalogue (ESA SP-1200, 1997; CDS VizieR I/239)
  installed with the extension.  All 115 star names of PyEphem's catalog are
  supported (multi-word names use underscores, e.g. $almanac.kaus_australis.rise).
- Anything Skyfield does not compute (e.g., the moon's libration, Jupiter's
  central meridian longitudes, stars when the catalog is not enabled) falls
  through to WeeWX's built-in almanac when PyEphem is installed.  Coverage was
  audited against the built-in almanac: with PyEphem installed, everything the
  built-in almanac can do continues to work; without PyEphem, all tags of the
  standard skins (and much more) work with Skyfield alone.
- Add replace_builtin_almanac field to the Celestial section of weewx.conf
  (default: true).  Set to false to leave report generation on the
  built-in almanac.
- The Celestial sample report is no longer empty at report generation time:
  every value on the page is now computed with the Skyfield almanac when the
  report is generated (formatted exactly as the javascript renders it), and
  the javascript then keeps the values updated from loop data on every loop
  record, as before.  So the page is now meaningful even when fetched
  without javascript (e.g., with curl).
- Add a pytest test suite (tests/test_almanac.py), including permanent parity
  audits against the built-in almanac.  Run with:
  /path/to/weewx-venv/bin/python -m pytest tests
- Bug fixes in the loop packet code:
  * daySunshineDur was wrong (or missing, due to a crash that was caught and
    logged) around the polar day/night transitions: on the first day of polar
    day (sun rises and never sets), on days when the sun is up at local
    midnight (it could go negative), and the sunset computation indexed the
    wrong array when checking whether the sun set.
  * Earth-to-body distances were reported in miles instead of kilometers for
    stations using the METRICWX unit system.
  * The skyfield timescale is now built once instead of on every update.
  * Fixed a typo (blufftone) that would crash the error handler if setting
    up the observer failed.
  * The WeeWX version check now compares major version numbers instead of
    strings (a string comparison would misjudge a hypothetical WeeWX 10).
  * Cleaned up type annotations (mypy is now clean), renamed a variable that
    shadowed a Python builtin, and fixed the --help usage text.
